# Файл сценария: как написать и загрузить

**Сценарий** — это разговор, в котором бот узнаёт у клиента всё нужное и отдаёт вам готовую заявку. Весь сценарий записан в одном текстовом файле. В этом документе — что в файле писать и как его загрузить.

В этой же папке лежат готовые сценарии (`offer_interview.yaml`, `beauty_booking.yaml` и другие) — рабочие примеры того, что описано ниже.

## 1. Как загрузить

1. В админке откройте «Сценарии» → «Загрузить из файла».
2. Выберите файл (или несколько — по одному сценарию в каждом).
3. Админка сразу проверит файл. Если в нём ошибка — покажет, где именно, и ничего не сохранит.
4. Нажмите «Загрузить и включить». Сценарий начинает работать сразу, перезапускать ничего не нужно.

Что происходит при загрузке:

- **Сценария с таким `key` ещё нет** — он создаётся и включается в отмеченных каналах (канал — место, где бот разговаривает: сайт, Instagram, песочница).
- **Сценарий с таким `key` уже есть** — появляется его новая версия, и она становится рабочей. Старые версии остаются в истории: любую можно вернуть в редакторе сценария, ссылка «История версий».
- **Файл ничем не отличается от рабочей версии** — ничего не меняется: админка напишет «Без изменений», загружать нечего.
- **Диалоги, которые уже идут по этому сценарию**, доходят до конца по той версии, с которой начались. Новая версия — для разговоров, которые начнутся после загрузки. Чтобы проверить новую версию, начните новый диалог (например, в песочнице).

Файл уже работающего сценария можно получить в его редакторе: внизу «Для разработчиков» → «скачать файлом». Поправьте его и загрузите обратно.

Требования к файлу: текст в кодировке UTF-8, расширение `.yaml`, `.yml` или `.json`, не больше 500 000 знаков, один сценарий в одном файле.

Без админки то же делает команда на сервере: `zama load-scenarios <файл или папка> --tenant <тенант>`.

## 2. Самый маленький файл

```yaml
key: callback_request
title: Заявка на звонок
language: ru

start:
  questions:
    - key: wants_callback
      ask: Клиент просит, чтобы ему перезвонили?

fields:
  - key: name
    question: Как к вам обращаться?
  - key: phone
    type: phone
    question: На какой номер перезвонить?
```

Здесь всё обязательное: ключ, название, язык, когда начинать (`start`) и что спросить (`fields`). Остальное добавляется по необходимости.

## 3. Правила записи

Файл пишется в формате YAML: «имя: значение», вложенность показывают отступы в два пробела (не табуляция), элементы списка начинаются с `- `. Строка после `#` — комментарий, бот его не видит.

**Ключи.** Значения `key` (сценария, вопроса, проверки, варианта) — это имена для программы: маленькие латинские буквы, цифры и одиночные подчёркивания, начинаются с буквы, не длиннее 64 знаков. Годится: `main_offer`, `phone2`. Не годится: `MainOffer`, `main-offer`, `main__offer`, `2phone`, `оффер`. Клиент ключей не видит.

**Тексты.** Любой текст (название, вопрос, описание, проверка) пишется одним из двух способов:

```yaml
question: Как к вам обращаться?        # одна строка — текст на основном языке сценария

question:                               # или отдельно для каждого языка
  ru: Как к вам обращаться?
  uk: Як до вас звертатися?
```

Если текста на языке клиента нет, бот берёт текст на основном языке (`language`) и сам переводит. При загрузке админка только предупредит, каких переводов не хватает, — это не ошибка.

**Кавычки.** Текст нужно взять в кавычки, если в нём есть двоеточие с пробелом, если он начинается со знака (`"`, `'`, `[`, `{`, `*`, `&`, `!`, `%`, `@`, `|`, `>`, `-`, `?`) состоит из одних цифр или похож на время или дату (`10:00`, `2026-10-05`):

```yaml
title: "Интервью: оффер и позиционирование"
```

Слова `yes`, `no`, `on`, `off` здесь — обычный текст. Логических значений только два: `true` и `false`.

**Лишнее — ошибка.** Имя, которого нет в этом документе (опечатка, выдуманная настройка), файл не пройдёт проверку. Так опечатка не останется незамеченной.

**JSON.** Тот же сценарий можно записать в JSON — имена и значения те же.

## 4. Верхний уровень файла

| Имя | Обязательно | Что это |
|---|---|---|
| `key` | да | Ключ сценария. По нему админка понимает, новый это сценарий или новая версия старого. У работающего сценария не меняйте: получится другой сценарий. |
| `title` | да | Название — для вас, в админке и уведомлениях. |
| `language` | да | Основной язык текстов, код языка: `ru`, `uk`, `en`. |
| `description` | нет | Для чего сценарий, одной-двумя фразами. |
| `start` | да | Когда сценарий начинается — раздел 5. |
| `fields` | да | Вопросы, которые бот задаёт, — раздел 6. |
| `confirm` | нет | Показать клиенту собранное и попросить подтвердить — раздел 7. |
| `completion` | нет | Когда сценарий считается законченным — раздел 7. |
| `events`, `waiting` | нет | Ответ вашей системы (CRM) — раздел 8. |
| `resume` | нет | Что делать, если клиент пропал и вернулся, — раздел 9. |
| `cancel` | нет | Как понять, что клиент передумал, — раздел 9. |
| `incompatible_with` | нет | Сценарии, которые не идут одновременно с этим, — раздел 9. |
| `actions` | нет | Что делать с результатом: отправить вам, написать клиенту — раздел 10. |

## 5. `start` — когда сценарий начинается

Каждое сообщение клиента проверяется вопросами «да / нет» из `start`. У каждого вопроса есть вес (`weight`). Сценарий начинается, когда сумма весов ответов «да» дошла до порога (`threshold`).

```yaml
start:
  questions:
    - key: wants_offer_help            # свой вопрос: ключ + текст
      ask: Клиент хочет разобраться со своим предложением или позиционированием?
      weight: 2
    - field: niche                     # вопрос про поле: «в сообщении есть ответ на вопрос niche?»
    - field: main_offer
  threshold: 2                         # начать, если клиент прямо попросил (вес 2)
                                       # или сразу назвал и нишу, и предложение (1 + 1)
```

| Имя | Что это |
|---|---|
| `questions` | Список признаков, хотя бы один. Признак — либо свой вопрос (`key` + `ask`), либо ссылка на вопрос сценария (`field`: ключ из `fields`). |
| `weight` | Вес признака, целое от 1 до 100. Не указан — 1. |
| `threshold` | Порог. Обязателен, когда признаков больше одного. С одним признаком можно не писать. Порог не может быть больше суммы всех весов — такой сценарий не начался бы никогда. |

Вопрос в `ask` пишется про клиента в третьем лице и так, чтобы на него можно было ответить «да» или «нет»: «Клиент хочет записаться на услугу?».

## 6. `fields` — что бот спрашивает

Каждый элемент списка — один вопрос и одно место для ответа.

```yaml
fields:
  - key: niche
    type: text
    title: Ниша
    question: Чем вы занимаетесь? Какая у вас ниша?
    description: Сфера и конкретная ниша бизнеса клиента («маникюр в своём кабинете», а не просто «красота»).
    filters:
      - key: concrete_niche
        ask: Клиент назвал конкретную нишу, а не только общую сферу?
  - key: positioning
    question: Чем вы отличаетесь от конкурентов?
    ask_after: [niche]
```

| Имя | Обязательно | Что это |
|---|---|---|
| `key` | да | Ключ вопроса. Под этим именем ответ уходит в готовую заявку. В одном сценарии не повторяется. |
| `type` | нет | Какой ожидается ответ — таблица ниже. Не указан — `text`. |
| `title` | нет | Короткое название ответа для админки («Ниша»). Клиент его не видит. |
| `question` | да | Что спросить. Бот каждый раз формулирует вопрос заново своими словами, по смыслу этого текста. |
| `description` | нет | Что считается ответом. По этому тексту бот понимает, есть ли в сообщении ответ именно на этот вопрос. |
| `filters` | нет | Проверки ответа — см. ниже. |
| `ask_after` | нет | Ключи вопросов, после которых задаётся этот. Пока на них нет ответа, бот этот вопрос не задаёт. |

**Как бот разбирает ответы.** Каждое сообщение клиента проверяется сразу по всем вопросам, на которые ещё нет ответа, а не только по последнему заданному. Клиент может ответить на несколько вопросов одним сообщением и в любом порядке — бот это засчитает и не будет переспрашивать. Поэтому у похожих вопросов должны быть разные `description`: по ним бот отличает, к какому вопросу относятся слова клиента.

Бот задаёт вопросы в том порядке, в каком они записаны в файле, с учётом `ask_after`.

### Типы ответа

| `type` | Какой ответ | Что получите в заявке | Свои настройки |
|---|---|---|---|
| `text` | Любой текст | Слова клиента | — |
| `choice` | Один из вариантов | Выбранный вариант | `options` |
| `yes_no` | Да или нет | `yes` / `no` | — |
| `catalog` | Товар или услуга из вашего каталога | Название и код позиции | `catalog` |
| `date` | Дата («завтра», «в пятницу», «5.10») | Слова клиента и дата `2026-10-05` | `date` |
| `time` | Время | Слова клиента и время `14:30` | — |
| `phone` | Телефон | Номер в виде `+380501234567` | — |
| `email` | Почта | Адрес | — |
| `number` | Число | Число | `number` |
| `list` | Несколько пунктов (гости, позиции заказа) | Список | `items` |
| `attachment` | Фото или файл от клиента | Файл | `attachment` |
| `receipt` | Квитанция об оплате | Сумма, дата и номер платежа с квитанции | `receipt` |

Настройку типа можно писать только у вопроса этого типа: `options` у `text` — ошибка.

**`options`** — варианты для `choice`, не меньше двух:

```yaml
  - key: format
    type: choice
    question: Вам удобнее онлайн или в офисе?
    options:
      - key: online
        label: Онлайн
      - key: office
        label: В офисе
```

**`catalog`** — откуда брать позиции для `catalog`:

```yaml
    catalog:
      categories: [Стрижки, Окрашивание]   # только эти разделы каталога; пусто — весь каталог
      max_options: 5                        # бот перечислит позиции списком, если их не больше (от 2 до 10)
```

**`date`**:

```yaml
    date:
      allow_past: false       # true — дата в прошлом годится (день рождения); false — бот переспросит
      max_days_ahead: 60      # не дальше чем через столько дней; не указано — без ограничения
```

**`number`**:

```yaml
    number:
      min: 1
      max: 50
      integer: true           # только целое
```

**`items`** — настройки для `list`:

```yaml
    items:
      min_items: 2            # от 1 до 50; не указано — 1
      max_items: 6            # от 1 до 50; не указано — 10
      item_fields:            # из чего состоит каждый пункт; без этого пункт — просто текст
        - key: name
          label: Имя
        - key: service
          label: Услуга
          required: false     # без этой части пункт всё равно принимается; не указано — true
```

**`attachment`**:

```yaml
    attachment:
      kinds: [image, file]    # что принимать: image, video, audio, file
      max_items: 3            # сколько файлов, от 1 до 10; не указано — 1
```

**`receipt`** — что должно быть на квитанции:

```yaml
    receipt:
      amount: 500             # сколько должно быть оплачено…
      currency: UAH           # …и в какой валюте (три большие буквы); с amount обязательна
      recipients: ["ФОП Іваненко", "UA123456789"]   # получатель: имя, счёт или конец номера карты
      max_age_days: 3         # платёж не старше стольких дней (от 0 до 365)
      tolerance: 0            # на сколько сумма может отличаться
```

Вместо `amount` сумму можно взять из каталога: `amount_field` — ключ вопроса типа `catalog` (цена выбранной позиции), `quantity_field` — ключ вопроса типа `number` (умножить на количество). Без суммы бот не может проверить квитанцию сам, и каждая уходит на проверку человеку.

### `filters` — проверки ответа

Проверка — вопрос «да / нет» про ответ клиента. Ответ принят, когда на все проверки вопроса получено «да». Если нет — бот уточняет.

```yaml
    filters:
      - key: has_price
        ask: Клиент назвал цену или диапазон цен?
```

| Имя | Обязательно | Что это |
|---|---|---|
| `key` | да | Ключ проверки, внутри одного вопроса не повторяется. |
| `ask` | да | Вопрос про ответ клиента, на который можно ответить «да» или «нет». «Да» — ответ годится. |
| `yes`, `no` | нет | Свои слова вместо «да» и «нет», если так проверка звучит точнее. Обычно не нужны. |

У вопросов типа `attachment` и `receipt` проверок быть не может: картинки проверяет программа, а не вопрос.

## 7. Подтверждение и завершение

**`confirm`** — когда все ответы собраны, бот показывает их клиенту и просит подтвердить:

```yaml
confirm:
  question: Проверьте, пожалуйста. Всё верно?

confirm: {}       # то же самое со стандартным вопросом «Всё верно?»
```

**`completion`** — когда сценарий считается законченным:

| Значение | Когда закончен |
|---|---|
| `all_fields` | На все вопросы есть принятые ответы (и клиент подтвердил, если есть `confirm`). Так по умолчанию. |
| `explicit_yes` | То же, и подтверждение клиента обязательно, даже если `confirm` не написан. |
| `external_event` | Ответы собраны, дальше бот ждёт ответа вашей системы — раздел 8. |
| `receipt` | Ответы собраны и квитанция принята. Нужен хотя бы один вопрос типа `receipt`. |

## 8. Ответ вашей системы: `events` и `waiting`

Нужны только при `completion: external_event`. Бот собрал заявку и ждёт, что скажет ваша система (CRM): записала, время занято, отказала. Система присылает событие запросом `POST /v1/events`, а в `events` написано, что с ним делать.

```yaml
completion: external_event

events:
  booked:                     # имя события — его присылает ваша система
    result: completed
    say: Готово! Вы записаны на {service} {date} в {time}.
  slot_taken:
    result: reopen
    reopen_fields: [date, time]
    say: Это время уже занято. Выберите, пожалуйста, другой день или время.
  failed:
    result: cancelled

waiting:
  hours: 24                   # ждать не дольше; потом сценарий закрывается как незаконченный
```

| Имя | Что это |
|---|---|
| `result` | `completed` — сценарий закончен; `cancelled` — отменён; `reopen` — вернуться к клиенту и спросить заново вопросы из `reopen_fields`. |
| `reopen_fields` | Ключи вопросов, которые задать снова. Обязательны при `reopen`, в остальных случаях не пишутся. |
| `say` | Что бот напишет клиенту. `{ключ_вопроса}` заменяется ответом клиента, `{data.имя}` — значением из данных события. |
| `hours` | Сколько часов ждать событие. Не указано — ждать без срока. |

## 9. Клиент пропал, передумал, начал другое

**`resume`** — клиент вернулся после паузы:

```yaml
resume:
  mode: within_hours          # always — продолжать когда угодно (анкета, интервью), так по умолчанию;
  hours: 24                   # within_hours — продолжать только в пределах hours (запись, заказ):
                              # позже сценарий закрывается как незаконченный, новый начнётся с нуля
```

**`cancel`** — как понять, что клиент передумал. Опишите это простыми словами — бот сверяет с этим каждое сообщение и закрывает сценарий:

```yaml
cancel:
  description: Клиент говорит, что запись ему не нужна, или просит прекратить вопросы.
```

**`incompatible_with`** — ключи сценариев, которые не могут идти одновременно с этим:

```yaml
incompatible_with: [cancel_booking]
```

## 10. `actions` — что делать с результатом

Каждое действие — «когда» (`on`) и «что сделать» (`do`).

```yaml
actions:
  - on: completed
    do: http_post
    endpoint: results_api
  - on: silence
    after_minutes: 15
    do: http_post
    endpoint: results_api
    status: incomplete
  - on: completed
    do: message_client
    params:
      text: Спасибо! Менеджер свяжется с вами в течение часа.
```

**Когда — `on`:**

| Значение | Когда срабатывает |
|---|---|
| `started` | Сценарий начался. |
| `field_filled` | Принят ответ на вопрос. |
| `field_stuck` | Бот несколько раз переспросил и так и не получил годного ответа. |
| `all_fields` | На все вопросы есть ответы. |
| `confirmed` | Клиент подтвердил собранное. |
| `waiting` | Заявка собрана, бот ждёт ответа вашей системы (`completion: external_event`) — момент отправить заявку в CRM. |
| `completed` | Сценарий закончен. |
| `cancelled` | Клиент передумал. |
| `abandoned` | Сценарий закрыт как незаконченный: вышло время `resume` или `waiting`. |
| `silence` | Клиент молчит. Через сколько минут — в `after_minutes`. |

**Что сделать — `do`:**

| Значение | Что делает | Что нужно указать |
|---|---|---|
| `http_post` | Отправляет собранное в вашу систему. | `endpoint` — имя адреса из «Настройки → Адреса доставки». |
| `notify_telegram` | Пишет вашей команде в Telegram. | `params.notifier` — имя из «Настройки → Уведомления». |
| `notify_email` | Пишет вашей команде на почту. | `params.notifier` — имя из «Настройки → Уведомления». |
| `message_client` | Бот пишет клиенту. | `params.text` — текст. |
| `handover` | Бот замолкает, диалог переходит человеку. | — |

**Остальные настройки действия:**

| Имя | Что это |
|---|---|
| `endpoint` | Имя адреса доставки для `http_post`. |
| `params` | Настройки самого действия: `notifier` или `text`. |
| `after_minutes` | Только для `silence`: сколько минут молчания. Не указано — берётся из настроек бота. |
| `status` | Статус, с которым уйдёт заявка. Обычно не нужен: статус ставится по событию. Пример: `incomplete` для заявки, которую клиент не закончил. |
| `field` | Только для `field_filled` и `field_stuck`: ключ вопроса, чтобы действие срабатывало на него одного. |
| `requires_approval` | `true` — действие ждёт, пока человек из команды нажмёт «одобрить». |

Адрес доставки и уведомление с такими именами должны быть заведены в админке, иначе действию некуда отправлять.

## 11. Полный пример

Этот файл можно загрузить как есть — он рабочий. Его же отдаёт кнопка «Скачать пример».

```yaml
# Заявка на консультацию: бот узнаёт имя, тему, формат, день и телефон,
# показывает собранное клиенту и после подтверждения благодарит.
key: consultation_request
title:
  ru: Заявка на консультацию
  uk: Заявка на консультацію
language: ru
description: Бот принимает заявку на консультацию и передаёт её вам.

start:
  questions:
    - key: wants_consultation
      ask: Клиент хочет записаться на консультацию или просит, чтобы его проконсультировали?
      weight: 2
    - field: topic
    - field: day
  threshold: 2            # попросил консультацию — или сразу назвал и тему, и день

fields:
  - key: name
    title: Имя
    question:
      ru: Как к вам обращаться?
      uk: Як до вас звертатися?
    description: Имя клиента — как его называть в разговоре.

  - key: topic
    title: Тема
    question: С каким вопросом вы хотите прийти на консультацию?
    description: О чём клиент хочет поговорить на консультации — его задача или проблема.
    filters:
      - key: concrete_topic
        ask: Клиент назвал конкретный вопрос или задачу, а не только «нужна консультация»?

  - key: format
    type: choice
    title: Формат
    question: Вам удобнее онлайн или в офисе?
    options:
      - key: online
        label: Онлайн
      - key: office
        label: В офисе

  - key: day
    type: date
    title: День
    question: В какой день вам удобно?
    date:
      max_days_ahead: 60

  - key: phone
    type: phone
    title: Телефон
    question: Оставьте, пожалуйста, номер телефона — мы подтвердим время.
    ask_after: [name]

  question: Проверьте, пожалуйста, заявку. Всё верно?

completion: all_fields

resume:
  mode: within_hours
  hours: 48

cancel:
  description: Клиент говорит, что консультация ему не нужна, или просит не задавать вопросы.

actions:
  - on: completed
    do: message_client
    params:
      text: Спасибо! Заявку получили, скоро свяжемся с вами.
  # Чтобы заявка уходила в вашу систему, заведите адрес в «Настройки → Адреса доставки»
  # и уберите решётки:
```

## 12. Что проверяется при загрузке

**Ошибки** — файл не сохраняется, админка пишет, что не так:

- файл написан с нарушением записи (сбился отступ, не закрыта кавычка) — показывается номер строки;
- нет обязательного (`key`, `title`, `language`, `start`, `fields`, у вопроса — `key` и `question`);
- незнакомое имя или опечатка в имени;
- ключ написан не по правилам или повторяется;
- ссылка на вопрос, которого нет (в `ask_after`, `start`, `reopen_fields`, `field` действия);
- вопросы ждут друг друга по кругу через `ask_after`;
- у `choice` меньше двух вариантов; настройка типа стоит не у того типа;
- порог `threshold` не указан при нескольких признаках или больше суммы весов;
- `completion: external_event` без `events`, или `events` / `waiting` при другом `completion`;
- `resume` с `within_hours` без `hours`;
- действию не хватает нужного: `endpoint`, `params.notifier` или `params.text`.

**Предупреждения** — файл сохраняется, но стоит посмотреть:

- у текста нет перевода на один из языков бота (бот переведёт сам);
- основной язык сценария не входит в языки бота;
- у квитанции не с чем сверить сумму — каждая уйдёт на проверку человеку.

## 13. Как писать вопросы и проверки

- **`question`** — так, как спросил бы человек. Бот не повторяет текст дословно, а задаёт вопрос по его смыслу.
- **`description`** — что именно считается ответом и чем он отличается от ответов на соседние вопросы. Чем больше в сценарии похожих вопросов («кто ваши клиенты» и «кому вы не подходите»), тем важнее описания: без них слова клиента могут уйти не в тот вопрос.
- **`filters`** — про качество ответа, а не про тему. «Клиент назвал конкретную нишу, а не общую сферу?» — хорошо. Одна проверка — одно требование.
- **Вопросы `start`** — про намерение клиента, а не про слова в сообщении: «Клиент хочет записаться на услугу?», а не «Есть ли слово „запись“?».
- **Не дробите** один ответ на несколько вопросов и не склеивайте разные ответы в один вопрос: один вопрос — одно, что вам нужно узнать.

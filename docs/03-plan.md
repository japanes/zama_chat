## 1. Что строим

- **Универсальный бот** для любого бизнеса: услуги, товары, интервью, что угодно. Ядро ничего не знает о салонах и товарах. Всё предметное описывается в сценариях.
- **Первый канал — Instagram Direct.** Есть режим оператора: бот предлагает варианты ответа, человек выбирает.
- Отдельный сервис: **своя БД и своя веб-админка, без Directus.**
- Общение только через **HTTP POST**, без сокетов.
- Код пишем заново, по принципам старого бота. **Отработанные промпты берём как есть** (`legacy-prompts/`), меняем только подставляемые списки.
- **Jev** (модель для решений: отвечает на вопросы да/нет, выбор, оценка — с уверенностью) встроен в архитектуру сразу. Пока доступа нет, на те же вопросы отвечает LLM через тот же интерфейс.

## 2. Термины

| Термин | Что значит |
|---|---|
| **Сценарий** | Разговор с целью: запись, заказ, интервью. Это набор полей + условие завершения + действия |
| **Поле** | Один кусок данных, который надо получить от клиента: услуга, дата, ниша, телефон |
| **Фильтры поля** | Проверочные вопросы Jev к ответу клиента: «назван конкретный адрес?», «понятна проблема клиента?». Ответ принят, только если прошёл все фильтры |
| **Маршрут** | Решение на текущее сообщение: какой сценарий, нужен ли поиск, нужен ли человек |
| **Результат** | Всё, что собрал сценарий. Хранится отдельно от диалога и имеет постоянный номер |
| **Действие** | «Когда случилось X → сделать Y»: отправить JSON во внешний API, уведомить, написать клиенту… |

## 3. Как обрабатывается сообщение

Шаги идут **строго по очереди** и делают **только нужную работу**.

1. **Приём.** В Директе клиенты пишут несколькими короткими сообщениями подряд. Ждём паузу в несколько секунд и склеиваем их в одно.
2. **Переписывание вопроса (LLM, всегда).** Контекст-менеджер делает из реплики самостоятельный вопрос: «да», «а это сколько?» → полная формулировка. Это нужно для поиска в Qdrant и ES. Промпты старые (раздел 4).
3. **Маршрут (Jev).** Один пакетный запрос по компактному состоянию диалога: история целиком не передаётся, у Jev 32 тыс. токенов. Вопросы:
   - безопасность и служебные типы: запрещённые темы, «просто привет / пока», «ты бот?»;
   - хочет ли клиент живого человека;
   - сценарий: начать / продолжить / отменить; активный сценарий имеет приоритет;
   - нужен ли поиск и какой: база знаний / каталог / не нужен;
   - вопросы к полям: для неактивных сценариев — поля-признаки («назвал услугу?», «назвал дату?»), для активного — все незаполненные поля. Одинаковые вопросы не дублируются.
4. **Данные.** Только те запросы в БД, Qdrant, ES и внешние API, которые нужны выбранному маршруту.
5. **Ответ (LLM).** Либо сразу ответ клиенту, либо 3–4 варианта для оператора (раздел 9).
6. **Действия и журнал.** Срабатывают действия сценария. Ход сохраняется целиком: что пришло, как переписали, что решил Jev/LLM, что нашли, что ответили, сколько стоило.

## 4. Контекст-менеджер

- Переписывание вопроса **всегда делает LLM**. Jev не спрашиваем, «уточнение ли это к прошлому сообщению».
- Основа — старые промпты:
  - `context_manager_question.txt` — главный: «дан диалог и одна строка из него, сделай строку самостоятельной». Ясное не трогать; при нескольких подходящих вариантах не угадывать; общие слова («брови», «ногти») не конкретизировать;
  - правила из `context_manager.txt`: сленг, несколько вопросов в одном сообщении, ответ на текущий шаг сценария сохранять как есть, язык.
- Подставляемые списки (типы, роли) заполняем из сценариев и персон нового бота. Сами тексты правил не меняем.
- Тип/роль/маршрут контекст-менеджер **больше не определяет** — это шаг 3 (Jev).

## 5. Слой решений (Jev)

**Интерфейс** повторяет форму API Jev:

```
decide(state, questions) → ответы с уверенностью
вопрос: noul (да/нет) | choice (выбор) | score (оценка)
```

- Сейчас — `LLMDecider` (LLM отвечает в JSON), потом `JevDecider`. Остальной код замены не заметит.
- **Журнал решений:** вопрос, ответ, уверенность, кто ответил (LLM/Jev), время, цена. Нужен, чтобы настроить пороги и честно сравнить Jev с LLM.
- **Теневой режим:** Jev отвечает параллельно, ответ пишется в журнал, но не используется. Переключаемся, когда по журналу видно, что Jev не хуже.
- Большой набор вопросов режем на пачки и шлём параллельно.

**Где работает Jev:**

| Место | Что решает | Тип |
|---|---|---|
| Маршрут (шаг 3) | безопасность, служебные типы, «хочет человека», сценарий, нужен ли поиск, поля-признаки | choice / noul |
| Фильтры полей | прошёл ли ответ клиента каждый проверочный вопрос | noul |
| Поиск | подходит ли каждый из ≤100 кандидатов, оценка для сортировки | noul / score |
| База знаний | отвечает ли найденный кусок текста на вопрос | score |
| Выбор из показанного | «давайте второй», «тот, что дешевле» → какой из последних показанных вариантов | choice |

**Что Jev не делаем:** даты, время, числа, суммы (это слабое место Jev — их извлекает код, при неудаче LLM), переписывание вопроса и тексты ответов (LLM).

## 6. Сценарии

### 6.1 Поле

Типы полей: выбор из каталога, короткий список вариантов, да/нет, дата, время, телефон, email, число, свободный текст, список (повторяющийся набор полей, например несколько гостей), вложение (фото, файл).

Настройки поля в админке:
- вопрос клиенту;
- фильтры Jev (проверочные вопросы);
- **«задавать после»** — список полей, которые должны быть заполнены раньше. Пример: «позиционирование» — после «ниши» и «оффера».

Состояние поля:
- **пусто** — ответа нет;
- **частично** — ответ есть, но часть фильтров не пройдена. Храним ответ и список непройденных фильтров;
- **заполнено** — все фильтры пройдены.

### 6.2 Правила заполнения

- Клиент может ответить на любое поле в любой момент. Ответ сохраняется сразу. «Задавать после» решает только, **когда бот спрашивает**.
- Ранний ответ (данный до своей очереди) **перепроверяется фильтрами, когда приходит его очередь**, — теперь уже с контекстом прошлых ответов. Даже если сначала прошёл.
- **Лимита попыток нет.** Поле должно быть заполнено полностью — бот дожимает. Пример: у салона 5 адресов, клиент не сказал какой → спрашиваем, пока не скажет. Выходы только три: клиент отменил / замолчал (таймаут) / ушёл к оператору.
- **Переспрос строится из непройденных фильтров:** LLM превращает их в уточняющий вопрос и опирается на уже сказанное («Вы говорили, что курсы премиум. А для кого именно?»). Новый ответ склеивается с частичным и проверяется заново. *Это гипотеза — проверим на практике.*
- Переспрашиваем каждый раз по-новому. Для полей с выбором показываем варианты списком.
- Когда бот формулирует вопрос, LLM видит прошлые ответы, чтобы вопрос звучал по делу.

### 6.3 Сценарий

**Статусы:**
- **в фокусе** — только один; бот задаёт вопросы по нему;
- **на паузе** — открыт, принимает данные, но бот о нём не спрашивает;
- **ждёт события** — данные собраны, ждём оплату / ответ CRM / оператора;
- **завершён**;
- **отменён**.

**Правила:**
- Открытых сценариев может быть несколько. Когда сценарий в фокусе завершился, бот **сразу** переходит к следующему на паузе.
- О сценариях на паузе бот напоминает в пределах 24-часового окна Директа (после 24 часов Instagram не даёт писать первым).
- Несовместимые пары сценариев задаются в админке.
- «Запишите меня и маму» — отдельный сценарий «групповая запись», а не две копии одиночной.
- Бот только ведёт диалог и собирает данные. **Выводов и анализа сам не делает** (например, в интервью про оффер).

**Условия завершения** (выбираются в сценарии):
- все поля собраны (неявное подтверждение: например, для записи дали все данные, включая телефон);
- явное «да» от клиента;
- внешнее событие: оплата прошла, CRM подтвердила, оператор подтвердил;
- клиент прислал чек (раздел 8).

## 7. Результаты и действия

### 7.1 Результат

- Каждый запущенный сценарий создаёт **результат** — отдельную запись в БД с постоянным номером. Для записи в салон это запись, для интервью — ответы.
- В админке — список результатов с фильтрами и статусами; каждый открывается вместе с перепиской.
- «Вы записаны» и подобное бот пишет **только после того, как действие реально прошло** (CRM ответила «ок»).

### 7.2 Действия

**Когда срабатывает:** поле заполнено / все поля собраны / клиент подтвердил / сценарий завершён / отменён / клиент молчит N минут.

**Что делает:**
- запрос во внешний API (в т.ч. отправка результата JSON);
- уведомление: админка, Telegram, email;
- сообщение клиенту;
- запуск другого сценария;
- передача диалога оператору.

Флаг **«нужно одобрение человека»**: действие ждёт, пока оператор нажмёт «одобрить» (карточка в очереди, раздел 9).

### 7.3 Отправка результата во внешний API — обязательно

- Настройки в админке: URL, ключ доступа, когда отправлять.
- В JSON **только собранные поля**. Без переписки, без выводов.
- Клиент замолчал на **15 минут** (настраивается) → уходит частичный результат со статусом «не закончено».
- Клиент вернулся → сценарий продолжается; в конце уходит повторная отправка **с тем же номером результата** и статусом «завершено». Внешний сервис просто обновляет запись.
- Если внешний сервис не ответил — повторяем. В админке видно «отправлено / ошибка» и есть кнопка «отправить ещё раз».
- У каждой отправки свой номер, чтобы внешний сервис мог отбросить дубль.
- Ответ внешнего API клиенту не показываем.

Пример (черновик формата):

```json
{
  "event": "scenario.completed",
  "result_id": "…",
  "delivery_id": "…",
  "scenario": "offer_interview",
  "status": "completed",
  "client": {"channel": "instagram", "id": "…", "username": "…"},
  "fields": {"niche": "…", "audience": "…", "main_offer": "…"},
  "missing": [],
  "started_at": "…",
  "finished_at": "…"
}
```

## 8. Проверка чеков об оплате

- LLM с распознаванием изображений вытаскивает из скриншота или выписки сумму, валюту, дату, получателя.
- Код сверяет с заказом и проверяет, не присылали ли этот чек раньше.
- **По умолчанию проверяет человек.** Отключить может только владелец или админ (не оператор). Отключение пишется в журнал.
- Даже при отключённой проверке человеку уходят: любые расхождения и суммы выше порога (порог задаёт владелец, отдельно по валютам).

## 9. Каналы и режим оператора

**Instagram Direct (первый канал):**
- приём сообщений через вебхук Meta, отправка через их API;
- склейка нескольких сообщений подряд (шаг 1);
- учёт 24-часового окна;
- фото и файлы — как вложения (для чеков и полей-вложений).

**Режим оператора** (включается для канала/аккаунта):
- бот не отвечает сам, а даёт 3–4 варианта ответа;
- оператор выбирает один кликом, может отредактировать, ответ уходит клиенту;
- клиент дописал → варианты пересобираются; оператор ответил сам → варианты снимаются;
- очередь с карточками двух видов: **«выбрать ответ»** и **«одобрить действие»**.

**HTTP API:** `POST`-методы для сообщений; тот же конвейер используют все каналы. Веб-виджет — позже, на том же API.

## 10. Поиск

- **Elasticsearch — каталог** (услуги, товары): поиск по словам, окончания (украинский анализатор), опечатки, фильтры по характеристикам («до 1000 грн, размер M»).
- **Qdrant — база знаний** (FAQ, страницы, файлы) и поиск по каталогу «по смыслу» («что-нибудь для сухой кожи»).
- Поиск за **одним общим интерфейсом**. Сценарий сам указывает, какой поиск нужен его полю.
- **Каталог любого размера:** поиск отбирает **до 100 кандидатов**, дальше их уточняет Jev. Если в каталоге меньше 100 позиций — Jev получает весь каталог без поиска.
- **База знаний:** Jev оценивает найденные куски. Если ни один не отвечает на вопрос — бот честно говорит «не знаю» или зовёт оператора.
- Цены, размеры и даты из запроса для фильтров извлекает код (при неудаче LLM), не Jev.
- **Живые данные** (цены, наличие, свободные слоты) берём из API клиента в момент запроса, а не из индекса.
- **Индексация** — фоновые задачи; запись в ES и Qdrant делает одна задача с повторами, чтобы базы не расходились; неизменённое по хешу не переиндексируем.
- На один вопрос — 1–2 запроса в поиск, а не 150, как в старом боте.

## 11. Админка

**Роли:**
- **владелец** — всё, включая порог сумм для чеков;
- **админ** — настройки, сценарии, отключение проверки чеков;
- **оператор** — диалоги, очередь, выбор ответов, одобрение действий.

**Разделы:**
1. Компании и пользователи.
2. Каналы (Instagram-аккаунты), режим оператора.
3. Сценарии: поля, фильтры, «задавать после», условия завершения, действия, несовместимые пары.
4. Результаты: список, статусы, статус отправки, «отправить ещё раз».
5. Очередь оператора.
6. Диалоги с разбором каждого хода (что переписали, что решил Jev/LLM, что нашли).
7. Промпты (с версиями).
8. Каталог и база знаний: источники, индексация, тестовый поиск.
9. Решения: LLM / Jev / теневой режим, журнал, уверенность.
10. Модели LLM и расходы.
11. Песочница: тестовый чат прямо в админке.

## 13. План работ

Идём «сквозными кусками»: после каждого этапа есть что потрогать руками.

### Этап 0. Каркас
- Репозиторий, `docker compose` (PostgreSQL), FastAPI, миграции БД, настройки, тесты.
- LLM-шлюз (один провайдер на старт).
- `POST /v1/messages` — принимает сообщение, отвечает через LLM. История в БД.

**Готово, когда:** можно отправить сообщение и получить ответ, ход записан в БД.

### Этап 1. Ядро хода
- Контекст-менеджер на старых промптах.
- Слой решений: интерфейс + `LLMDecider` + журнал решений.
- Маршрут: безопасность, служебные типы, «хочет человека», выбор сценария.
- Генерация ответа (старые `system_prompt` / `user_prompt` как основа).
- Разбор хода в журнале.

**Готово, когда:** по журналу хода видно все шаги: как переписали вопрос, что решил маршрут, что ответили.

### Этап 2. Сценарии на примере интервью — **первая проверка на практике**
- Описание сценария (пока файлом или через API, редактор — на этапе 3).
- Поле «свободный текст», фильтры, «задавать после», состояния поля.
- Ранний ответ, перепроверка в свою очередь, дожимание, переспрос из непройденных фильтров.
- Статусы сценария: фокус / пауза / завершён / отменён; несколько сценариев сразу.
- Результат + действие «отправить JSON»: повторы, номер отправки, таймер тишины 15 минут, повторная отправка с тем же номером.

**Готово, когда:** интервью про оффер проходит целиком, JSON приходит на тестовый приёмник, частичный результат уходит через 15 минут тишины.

### Этап 3. Админка v1
- Вход, роли владелец / админ / оператор.
- Редактор сценариев (поля, фильтры, «задавать после», действия).
- Результаты и статус отправок, «отправить ещё раз».
- Диалоги с разбором хода, промпты, песочница.

**Готово, когда:** новый сценарий можно собрать и проверить в песочнице без программиста.

### Этап 4. Instagram Direct и оператор
- Вебхук Meta, отправка, склейка сообщений, 24-часовое окно, контакты.
- Режим оператора: 3–4 варианта, очередь, выбор / правка, пересборка и снятие вариантов.
- Уведомления (Telegram / email).
- Напоминания о сценариях на паузе.

**Готово, когда:** бот работает на реальном Instagram-аккаунте в обоих режимах.

### Этап 5. Каталог и поиск
- Qdrant: база знаний (FAQ, файлы, сайты), фоновая индексация.
- ES: каталог, характеристики, фильтры; синхронная запись в обе базы.
- Jev/LLM-уточнение до 100 кандидатов, оценка кусков базы знаний, «не знаю».
- Поле «выбор из каталога», выбор из последних показанных вариантов.
- Живые данные через API клиента.

**Готово, когда:** бот находит нужную услугу/товар по разговорной фразе и честно говорит «не знаю», если ответа нет.

### Этап 6. Сценарии с действиями во внешнем мире (запись, заказ, оплата)
- Остальные типы полей: дата, время, телефон, email, число, список, вложение — извлечение кодом, при неудаче LLM.
- Статус «ждёт события», входящие события (CRM, оплата, оператор).
- Флаг «нужно одобрение», карточки «одобрить действие».
- Несовместимые пары, групповая запись.
- Проверка чеков.

**Готово, когда:** запись в салон проходит от вопроса до подтверждения CRM, чек об оплате проверяется по правилам раздела 8.

### Этап 7. Jev
- `JevDecider`, теневой режим, сравнение с LLM по журналу, пороги, переключение.
- Можно начать на любом этапе, как только появится доступ.

**Готово, когда:** по журналу видно, на каких решениях Jev не хуже LLM, и они переключены на Jev.

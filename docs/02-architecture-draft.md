# Новый чат-бот: черновик архитектуры (для обсуждения)

Статус: **обсуждение, код не пишем**. Основание: `docs/01-ecom-chat-analysis.md`.

> **Частично устарел.** Актуальные решения и план работ — `03-plan.md`.

## Цели

- Отдельный сервис со своей БД и своей веб-админкой, без Directus.
- Общение только через HTTP POST, без сокетов.
- Код пишем заново, по принципам старого бота.
- Места под Jev закладываем сразу. Реализацию Jev делаем позже.

## Что такое Jev (кратко)

Jev — это «decision model» от TypeSafe AI, вышла 15.09.2026 в ограниченном доступе. Текст она **не пишет**. Ей передают «состояние» (текст диалога) и набор вопросов, а в ответ приходят числа с уверенностью. Типы вопросов:
- **noul**: да/нет, возвращает вероятность «да». Пример: «пользователь хочет живого оператора?» → 0.93.
- **choice**: выбор из вариантов, возвращает вероятность каждого варианта. Пример: намерение = запись / цена / жалоба / болтовня.
- **score**: оценка по шкале. Пример: насколько найденный документ подходит к вопросу.

Все вопросы одного запроса обрабатываются параллельно, поэтому 10 вопросов стоят по времени примерно как один. Разработчики заявляют, что Jev в 40–200 раз быстрее и в 40–400 раз дешевле обычных LLM на таких задачах. По их же словам, **Jev слаб на числах, датах и «враждебных» текстах** (попытках обмануть модель).

**Неизвестно:** поддерживает ли Jev русский и украинский, какой у него лимит контекста, какая задержка и есть ли у нас доступ.

Главный вывод: Jev не заменяет LLM. Он заменяет все **мелкие решения внутри конвейера**, которые сейчас делаются лишними вызовами LLM.

## Стек (предложение)

- Python + FastAPI, весь ввод-вывод асинхронный (httpx, async-версии SDK).
- PostgreSQL: настройки, промпты, база знаний (реестр), история, лог решений.
- Qdrant: поиск по знаниям.
- Redis: очередь фоновых задач (индексация, обход сайтов), кэш конфигурации, ограничение частоты запросов.
- Админка: отдельное SPA. Выбор фреймворка — открытый вопрос.
- Виджет: лёгкий JS без iframe или с iframe (обсудить).

## API

**Виджет (публичный):**
- `POST /v1/widget/session`: принимает `{widget_key, visitor_id}`, возвращает `{session_token, start_message, quick_replies}`.
  - Проверяем, что ключ существует, а Origin входит в список сайтов этого ключа.
  - Токен подписан сервером и содержит tenant и session. Тенант берётся **из токена**, а не из того, что прислал браузер.
- `POST /v1/widget/message` с токеном: принимает `{text}`, возвращает `{reply, quick_replies, turn_id, handoff}`.
- `POST /v1/widget/history`: история диалога.
- Если позже понадобится потоковый ответ, тот же POST с заголовком `Accept: text/event-stream` будет отдавать текст по кусочкам (SSE). Контракт при этом не ломается.

**Админка:** `/v1/admin/*`, вход по логину, роли.

**Каналы** (Telegram, Instagram): тонкие адаптеры, которые вызывают тот же конвейер.

## Ход диалога (конвейер)

`[J]` отмечает место, где решение принимает Jev. Пока его нет, это же решение делает LLM или простое правило.

```
POST /message
 1. LOAD      ContextManager.load(session) → состояние + история
 2. UNDERSTAND
      язык (lingua, детектор создаётся один раз)
      [J] один пакетный запрос: intent, is_followup, needs_knowledge, safety, wants_human
      LLM: переписать вопрос в самостоятельный — ТОЛЬКО если is_followup
 3. ROUTE
      safety = блок          → шаблонный ответ
      wants_human            → передача оператору (позже)
      активный сценарий или intent запускает сценарий → FLOW
 4a. FLOW     LLM извлекает значения полей (даты, время, имя)
              код проверяет значения (слот свободен? → API ecom)
              [J] «пользователь отменяет сценарий?», «подтверждает?»
 4b. RETRIEVE гибридный поиск в Qdrant → [J] оценка релевантности каждого кандидата → top-N
              факты (цены, слоты, записи) → инструменты (tools) через API ecom
 5. GENERATE  [J] выбор модели: простой вопрос → дешёвая, сложный → сильная
              LLM пишет ответ
 6. VERIFY    [J] «ответ опирается на найденное?», «отвечает на вопрос?»
              ниже порога → перегенерация / честное «не знаю» + флаг / оператор
 7. SAVE+ACT  сохранить ход, трассировку и все решения; действие сценария (запись)
→ JSON-ответ
```

## Context manager (новый)

В старом боте «context manager» — это просто LLM-вызов, который переписывает вопрос. Памятью он не управлял. Новый context manager отвечает именно за **память диалога**:

- **Состояние диалога** (`ConversationState`): язык, активный сценарий и заполненные поля, последние предложенные варианты («на какое время: 10:00 или 12:00?»), флаг оператора, краткое резюме старой части диалога.
- **История** хранится строками в таблице `messages`, по строке на сообщение, а не одним JSON на весь диалог.
- **Сборка контекста под бюджет токенов.** Порядок: system → персона → состояние → резюме → последние N ходов → найденные знания → вопрос. Если не помещается, сначала урезаем знания, а старые ходы сворачиваем в резюме.
- **Резюме** обновляет дешёвая модель в фоне, когда история перерастает порог.
- **Переписывание вопроса** выполняется только для продолжения разговора (решение `is_followup`). Самостоятельный вопрос не трогаем и экономим вызов.
- Никаких глобальных переменных: на входе данные, на выходе данные.

## Поиск (retrieval)

- **Предложение: для бота только Qdrant, без Elasticsearch.**
  - Одна коллекция, тенанты разделены полем `tenant_id` с индексом.
  - Два вектора на документ: смысловой (dense) и «по словам» (sparse, аналог BM25).
  - Запрос идёт по обоим сразу, результаты объединяются по местам в выдаче (RRF), поэтому ручные веса вроде 0.55/0.35 не нужны.
- Фильтры: тенант, язык, тип документа (FAQ / страница / файл / услуга).
- **Факты не ищем через эмбеддинги.** Цены, длительность, свободные слоты и записи берём инструментами из API ecom, так данные всегда актуальны.
- **Индексация:**
  - выполняется фоновыми задачами;
  - `id = uuid5(tenant, источник, номер куска)`;
  - по хешу содержимого пропускаем неизменённое, чтобы не платить за эмбеддинги повторно.
- Интерфейсы: `Embedder`, `Index`, `Retriever`, `Reranker`. Реранкер — место для Jev (`score` на кандидата).

## LLM-шлюз

- Один интерфейс `complete(role, messages, schema?, tools?)`.
- Провайдеры: OpenAI, Gemini, Nebius (OpenAI-совместимый).
- Модель выбирается по роли и тенанту.
- Клиенты создаются один раз.
- Токены и цена считаются в одном месте. Таймауты и повторы тоже.

## Слой решений (DecisionEngine) — место для Jev

Интерфейс сразу повторяет форму API Jev, чтобы потом только сменить реализацию:

```
decide(state, questions: {name: Question}) → {name: Decision}
Question = {type: noul|choice|score, instructions, options?}
Decision = {value, probs, confidence}
```

**Реализации:**
- `LLMDecider` — сейчас: LLM в JSON-режиме.
- `RuleDecider` — простые правила.
- `JevDecider` — позже, пока заглушка.

**Политика на каждое решение** настраивается в админке:
- порог уверенности;
- что делать ниже порога: спросить LLM, переспросить пользователя или передать оператору.

**Лог решений** (таблица `decisions`): вопрос, ответ, уверенность, провайдер, время, цена, фактический исход. Без этого лога нельзя настроить пороги и честно сравнить Jev с LLM.

**Теневой режим:** Jev работает параллельно, его ответ пишется в лог, но не используется. Переключаемся, когда по логу видно, что Jev не хуже.

### Точки решений

| # | Этап | Решение | Тип | Что заменяет в старом боте |
|---|---|---|---|---|
| 1 | Понимание | intent (намерение) | choice | часть LLM-вызова context manager |
| 2 | Понимание | is_followup (нужно ли переписывать вопрос) | noul | новое, экономит LLM-вызов |
| 3 | Понимание | needs_knowledge (искать ли в базе и где) | choice | новое, сейчас поиск идёт всегда |
| 4 | Понимание | safety: спам, оскорбления, вне темы, «ты бот?» | choice | типы `ethical_violation`, `not_a_bot` |
| 5 | Понимание | wants_human (просит оператора, раздражён) | noul | не было |
| 6 | Сценарий | начать / продолжить / отменить сценарий | choice | поля `type` / `disabled` context manager |
| 7 | Поиск | релевантность каждого кандидата | score | выключенный реранкер и формула 0.55/0.1/0.35 |
| 8 | Генерация | выбор модели (дешёвая / сильная) | choice | одна модель на тенанта |
| 9 | Проверка | ответ опирается на знания? отвечает на вопрос? | noul | quality manager (LLM) и эмодзи `:-(` |

**Что Jev НЕ отдаём:** извлечение дат, времени, чисел и цен (это его слабое место) и генерацию текста. Это остаётся за LLM и кодом.

Решения 1–5 идут **одним пакетным запросом**, потому что Jev считает вопросы параллельно.

## Сценарии (flows)

- Описываются в админке: шаги, поле, вопрос пользователю, проверка значения, действие в конце.
- Значения извлекает LLM по схеме. Проверяет их код: дата существует, слот свободен (запрос в API ecom).
- Действия подключаются как плагины (`booking.create`, `notify.telegram`, …). Всё, что относится к салонам, изолировано в интеграции с ecom.

## Данные (PostgreSQL), черновик

- `tenants`, `admin_users`, `widget_keys` (+ разрешённые сайты)
- `llm_providers`, `llm_models` (цены), `model_roles` (роль → модель для тенанта)
- `prompts` (с версиями), `personas`, `intents`
- `decision_policies` (порог, действие ниже порога, провайдер)
- `flows`, `flow_steps`
- `knowledge_sources` (Q&A / сайт / файл), `knowledge_chunks` (реестр: id в Qdrant, хеш), `index_jobs`
- `conversations` (состояние, резюме), `messages`, `turns` (трассировка хода: этапы, промпты, найденное, токены, цена), `decisions`
- `channel_identities` (веб, Telegram, Instagram → посетитель)

## Админка: разделы

1. Компании (тенанты) и пользователи.
2. Настройки виджета и код для вставки.
3. Модели и роли: какая модель на какую роль, ключи провайдеров.
4. Промпты с версиями, персоны, намерения.
5. База знаний: Q&A, сайты, файлы, статус индексации, тестовый поиск.
6. Сценарии: редактор шагов.
7. Решения: пороги, провайдер (LLM / Jev / теневой режим), статистика уверенности.
8. Диалоги: просмотр с трассировкой каждого хода, список «не знал ответа».
9. Расходы.
10. Песочница: тестовый чат прямо в админке с показом трассировки.
11. Позже: режим оператора.

## Порядок работ (черновой)

1. **Каркас:** POST API, LLM-шлюз, простой конвейер (понять → найти → ответить), история и context manager, виджет.
2. **База знаний:** Q&A, файлы, сайты, фоновая индексация, гибридный поиск.
3. **Админка:** тенанты, настройки, промпты, база знаний, просмотр диалогов.
4. **Сценарии и интеграция с ecom** (запись).
5. **Слой решений:** сначала на LLM, плюс лог решений и набор тестовых вопросов. Затем Jev в теневом режиме, затем переключение.
6. **Каналы и оператор:** Telegram, Instagram, режим оператора.

## Открытые вопросы

1. Бот только для салонов Zama или универсальный, для любого бизнеса? От этого зависит, будет запись ядром или плагином.
2. Каталог и записи: бот ходит в ecom по API (своя БД только для бота)? Или читает общую БД напрямую?
3. Убираем ES из бота и оставляем только Qdrant с гибридным поиском?
4. Эмбеддинги: OpenAI `text-embedding-3-large` (платно, внешний сервис) или своя модель (bge-m3: смысловой и словарный вектор одной моделью, ru/uk)?
5. Кто пользуется админкой: только наша команда или владельцы салонов тоже? От этого зависят роли и сложность интерфейса.
6. Есть ли доступ к Jev (ключ, early access)? Поддерживает ли он ru/uk?
7. Нужны ли в первой версии Telegram, Instagram и режим оператора?
8. Переносим ли данные из Directus: промпты, базу знаний, историю?
9. Нужен ли потоковый ответ (текст появляется по мере генерации) или хватит целого ответа?

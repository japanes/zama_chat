# zama_chat — подробный план реализации

## Контекст

Все решения по продукту приняты и записаны в `docs/03-plan.md`. Там же есть 8 этапов, но только крупными мазками. Теперь нужен план, по которому можно сразу писать код:
- структура репозитория и модулей;
- таблицы БД;
- контракты API;
- как устроен ход диалога внутри;
- по каждому этапу — задачи, файлы, тесты и «готово, когда».

Кода в проекте пока нет: в `zama_chat/` лежат только `docs/`, `tmp/` и `secrets/`. Старые промпты выгружены в `docs/legacy-prompts/`, их берём как есть.

**Jev доступен** (проверено 2026-10-02): Vercel AI Gateway, ключ лежит в `secrets/jev`, на счету $15. В каталоге Gateway есть:
- `typesafe-ai/jev` — тип evaluation, контекст 32k, вход $0.042 за 1М токенов, выход бесплатный;
- `openai/gpt-6-luna` — вход $0.10, выход $0.50 за 1М (до 272k токенов в запросе). Первая модель, которую заведём; в код не вшивается;
- `openai/text-embedding-3-large`.

Поэтому Jev — основной решатель с этапа 1, а не «этап 7 когда-нибудь».

5. Записать в память правило работы (feedback): в код вшиваем только единичные внешние вещи (Jev, адрес Gateway). 6. Записать в память (feedback): когда пользователь сказал «делай все этапы» — идти по всем этапам подряд без остановок и вопросов; тесты писать вместе с кодом, но не запускать — прогоняем потом вместе. И (project): админка zama_chat — дашборд в стиле factory, вход через Google или ссылкой на почту.

## Порядок работы (указание пользователя 2026-10-02, главное правило)

- **Все этапы 0–7 подряд, без остановок и без вопросов.** Пользователь у компьютера не будет; ничего критичного, что требует его подтверждения, тут нет.
- **Тесты пишем вместе с кодом (по спискам «Тесты» в каждом этапе), но НЕ запускаем** — прогоним и починим вместе, когда пользователь вернётся. Чтобы код хотя бы собирался, после каждого этапа — только статическая проверка: `ruff check` и `python -m compileall` (это не запуск тестов).
- **Всё, что «пользователь проверяет»** (набор пробы Jev, формулировки интервью), — пишу черновиком и помечаю `# TODO(review)`.
- **Что требует внешних аккаунтов** (Instagram, Google OAuth, SMTP, CRM) — код + переменные в `.env.example`, без подключения.
- **Проба Jev** — скрипт пишу, но не запускаю (это тоже проверка). До пробы служебные вопросы маршрута пишем по-английски, фильтры полей — на языках тенанта; язык вопросов — настройка.
- Коммит после каждого этапа (conventional commits).
- **Instagram сейчас не подключаем** (указание пользователя): код этапа 4 пишется, но приложение Meta и тестовый аккаунт заведём потом. Сначала испытываем бота без продуктов Meta — через HTTP API (`POST /v1/messages`) и песочницу админки, добиваемся правильных ответов.

## 1. Технические решения (по умолчанию)

| Что | Выбор | Почему |
|---|---|---|
| Язык, сборка | Python 3.12+, `uv`, `ruff` (длина строки 100), `pytest` + `pytest-asyncio` (auto). uuid7 — библиотека `uuid-utils` (в 3.12 его нет) | Как в других проектах пользователя (`obeds/api`) |
| Веб | FastAPI + uvicorn, pydantic v2, pydantic-settings | Решено в docs/02 |
| БД | PostgreSQL 16, SQLAlchemy 2 (async) + asyncpg, Alembic | Решено |
| HTTP-клиент | httpx (async), один клиент на процесс | В старом боте блокирующие `requests` |
| **Фоновые задачи** | **Таблица `jobs` в PostgreSQL** + отдельный процесс-воркер (`SELECT … FOR UPDATE SKIP LOCKED`, будит `LISTEN/NOTIFY`) | Задача записывается **в той же транзакции**, что и результат сценария. Если сервер упал, отправка не потеряется. Таймер тишины и склейка сообщений — это задачи с `run_at`, которые можно перенести. **Redis не нужен.** |
| Один ход за раз | **Аренда диалога** (lease): колонки `conversations.lease_owner`, `lease_until`, `state_version` | Два хода одного диалога никогда не идут одновременно. Ход делится на 3 части: короткая транзакция «взять» → вызовы LLM **вне транзакции** (10–30 секунд) → короткая транзакция «записать» (проверяем, что аренда всё ещё наша). Соединение из пула не простаивает. Если воркер упал, аренда истекает сама и ход повторяется. HTTP-канал ждёт аренду с таймаутом, потом отвечает 409 |
| Ответ клиенту | **Через исходящую очередь** (outbox): ответ пишется в `messages` со статусом `pending` + задача `send_message` в одной транзакции | Нет ни потерянных, ни двойных ответов при падении. В HTTP-канале ответ возвращается в теле запроса, задача не нужна |
| Время | `Clock` (интерфейс «который час»), в тестах — ручные часы | Таймеры тишины, склейки и истечения проверяются в тестах без ожидания |
| Админка | Nuxt (SPA, `ssr: false`) + Tailwind. **Дашборд как в factory** (`/home/japanes/projects/factory/frontend`): тот же каркас (`layouts/app.vue`, `AppSidebar` 260/72px со сворачиванием, `AppHeader` с переключателем языка, темы и меню пользователя, мобильное меню), тот же `tailwind.config.js` (цвета, радиусы, тени, тёмная тема `class`). **Вход — через Google или ссылкой на почту** (без паролей), как в factory. Интерфейс многоязычный: en, uk, ru, список расширяется (`@nuxtjs/i18n`) | Решено пользователем. Привычный вид и вход, на этом стеке почти все его проекты |
| Модели | **Jev + LLM, оба через Vercel AI Gateway** (Vercel оплачен; один ключ `AI_GATEWAY_API_KEY`). **Jev вшит** (он один): `typesafe-ai/jev`, свой httpx-клиент к `POST https://ai-gateway.vercel.sh/v1/evaluate` (§5 «Jev»). **LLM-моделей в коде нет ни одной**: админ сам заводит модель и её цены и назначает, какая модель на какой задаче (ответ клиенту и т.д.), переключение — сразу (§5 «Модели LLM»). Код говорит с ними через официальный SDK `openai` (async) с `base_url=https://ai-gateway.vercel.sh/v1`, поэтому годится любая модель из каталога Gateway; используем модели OpenAI, первой заведём `openai/gpt-6-luna` | Решено. Моделей много, нужную надо включать за минуту, без выкладки кода. Один ключ, цена каждого вызова приходит в ответе, логи и бюджеты — в кабинете Vercel. Минус: если Vercel лежит, не работают ни LLM, ни Jev; адрес Gateway — настройка, на прямой OpenAI переключается без правки кода. Структурированный ответ — `response_format` (json_schema) |
| Языки | У тенанта список языков и правило «язык клиента → язык ответа» (например ru и uk → uk, остальные → en). Сценарий — один файл с текстами на языках тенанта. Подробно — §5 «Языки» | Бизнес сам решает, на каких языках говорит бот |
| Логи | structlog в JSON, `turn_id` в каждой строке | Чтобы найти всё по одному ходу |
| Секреты | Токены каналов и ключи внешних API тенантов хранятся в БД зашифрованными (Fernet, ключ в env). Ключ Vercel `AI_GATEWAY_API_KEY` — только в env / `.env`, в логи и отчёты не попадает | В старом боте токены лежали в коде |
| Временные файлы | Только `<project>/tmp/` | Правило пользователя |

## 3. Данные (PostgreSQL)

У всех таблиц есть `tenant_id`. Все `id` — uuid (uuid7: отсортированы по времени).

| Таблица | Ключевые колонки | Этап |
|---|---|---|
| `tenants` | slug, title, settings jsonb (`languages`, `reply_language` — §5 «Языки»; описание бизнеса для `client_description`, таймер тишины) | 0 |
| `api_keys` | tenant_id, hash, title, revoked_at | 0 |
| `contacts` | channel, external_id, username, name; unique(tenant, channel, external_id) | 0 |
| `conversations` | contact_id, channel_id, client_language, reply_language, state jsonb (только служебное: `last_presented` и т.п.), operator_mode, last_client_at, last_bot_at, lease_owner, lease_until, state_version | 0 |
| `messages` | conversation_id, role (client/bot/operator/system), text, attachments jsonb, external_id, turn_id, processed_at, send_status (pending / sent / failed / dropped — для ответов бота); unique(tenant, channel, external_id) + `ON CONFLICT DO NOTHING` — Meta может прислать одно сообщение дважды | 0 |
| `turns` | conversation_id, input_text (склеенный), rewritten, route jsonb, trace jsonb, tokens, cost, duration_ms, error | 0 |
| `llm_calls` | turn_id, role, model, prompt_key + version, request, response, tokens_in/out, cost, latency_ms, generation_id (id запроса в логах Vercel) | 0 |
| `llm_models` | имя у Gateway (`openai/gpt-6-luna`), подпись, цены за 1М токенов (вход, кэшированный вход, выход), окно контекста, что умеет (схема JSON, `reasoning_effort`, картинки), is_active. Пустая — модели заводит админ | 0 |
| `model_roles` | tenant_id (null = общая настройка), role, model_id, reasoning_effort, timeout_s, fallback_model_id (запасная, если основная не ответила) | 0 |
| `prompts` | tenant_id (null = общий), key, version, body, is_active, author | 1 |
| `decisions` | turn_id, batch_id (один запрос к Jev), key, type (boolean/choice/score), question, answer jsonb (value, probabilities), confidence, provider (jev/llm), model, reason (primary / below_threshold / jev_error / shadow), used, latency_ms, tokens_in, cost, generation_id | 1 |
| `scenarios` | key, version, title, definition jsonb (проверяется `scenarios/schema.py`), is_active | 2 |
| `scenario_runs` (= **результат**) | conversation_id, scenario_id + version, status (focus / paused / waiting / completed / cancelled / abandoned), fields jsonb, delivery_seq, started_at, finished_at, last_activity_at. Уникальные индексы: не больше одного `focus` на диалог; не больше одного открытого запуска одного сценария на диалог | 2 |
| `endpoints` | внешние адреса: url, secret (зашифрован), headers | 2 |
| `deliveries` | id (= номер отправки), run_id, endpoint_id, event, payload, status, attempts, last_code, last_error, sent_at | 2 |
| `jobs` | kind, payload, run_at, status, attempts, max_attempts, locked_until, last_error, dedupe_key (unique только среди `queued`: задачу, которая уже выполняется, перенести нельзя — ставится новая) | 0 |
| `users` / `memberships` / `audit_log` | email, name, avatar_url, google_sub, is_superadmin, locale (язык интерфейса админки: en / uk / ru); роль в тенанте (owner/admin/operator); кто что поменял | 3 |
| `login_tokens` / `sessions` | ссылка на почту: хеш токена, email, срок 15 мин, used_at; сессия: хеш токена из cookie, user_id, expires_at, last_seen_at | 3 |
| `channels` | kind (http / instagram), title, account_id, username, token (зашифрован), token_expires_at, status (connected / expiring / error / disabled), settings (operator_mode, пауза склейки; по желанию — свои `languages`, `reply_language`, описание бизнеса поверх настроек тенанта). Unique(kind, account_id) на всю систему: один аккаунт — один тенант. У тенанта сколько угодно каналов. API-ключ привязан к своему каналу kind=http | 0 (http), 4 (instagram) |
| `channel_scenarios` | channel_id, scenario_key, position, is_enabled — какие сценарии работают в этом канале и в каком порядке (порядок решает фокус при равенстве) | 2 |
| `operator_tasks` | conversation_id, kind (choose_reply / approve_action / review_receipt), payload, status, resolved_by | 4 |
| `catalog_items`, `knowledge_sources`, `knowledge_chunks` | хеш содержимого, id в ES/Qdrant | 5 |
| `receipts` | run_id, image, извлечённые поля, хеш (против повторов), решение, кто проверил | 6 |

**Сценарий хранится одним JSON с версией**, а не раскладывается на таблицы полей и фильтров (в docs/03 были `scenario_fields`, `field_filters`). Так проще менять формат и хранить версии: результат ссылается на ту версию сценария, по которой его собрали.

**Состояние поля** внутри `scenario_runs.fields`:
```json
{"niche": {"state": "partial", "value": "…", "failed_filters": ["concrete_niche"],
           "needs_recheck": false, "message_ids": ["…"], "updated_at": "…"}}
```

## 4. Формат сценария (YAML → `definition`)

Ниже — набросок, с которого формат начинался. Действующее полное описание, по которому пишут файл сценария и загружают его через админку («Сценарии» → «Загрузить из файла»), — в документации админки, страница `/docs/scenario-file` (тексты на трёх языках интерфейса: `admin/docs/<язык>/scenario-file.md`); тест `tests/unit/test_scenario_docs.py` следит, чтобы они не отставали от кода и друг от друга.

```yaml
key: offer_interview
title: "Интервью: оффер и позиционирование"
language: uk                 # основной язык: с него LLM переводит, если текста на нужном языке нет
start:                       # когда сценарий запускается: вопросы Jev «да/нет» с весами
  questions:
    - key: wants_offer_help
      ask:
        uk: Клієнт хоче розібратися зі своєю пропозицією та позиціонуванням?
        en: Does the client want to sort out their offer and positioning?
      weight: 2              # одного этого «да» хватает (вес = порогу)
    - field: niche           # вопрос поля: «в сообщении есть ответ про нишу?»
    - field: main_offer      # вес по умолчанию 1
  threshold: 2               # запуск, когда сумма весов ответов «да» ≥ 2
                             # «2 из 3» = у всех вес 1, порог 2
fields:
  - key: niche
    type: text               # этап 2: text, choice, yes_no; этап 6: date, time, phone, email, number, list, attachment
    question:                # тексты на языках тенанта (languages)
      uk: Чим ви займаєтесь? Яка у вас ніша?
      en: What do you do? What is your niche?
    filters:                 # проверочные вопросы Jev (boolean «да/нет»), все должны пройти
      - key: concrete_niche
        ask:
          uk: Клієнт назвав конкретну нішу, а не загальну сферу?
          en: Did the client name a specific niche, not a general field?
  - key: main_offer
    question: Що саме ви продаєте?   # просто строка = только основной язык; для en админка предупредит
  - key: positioning
    question: …
    ask_after: [niche, main_offer]
    filters: […]
completion: all_fields       # all_fields | explicit_yes | external_event | receipt
resume:                      # клиент вернулся после долгой паузы
  mode: always               # always — продолжать когда угодно (профиль, интервью)
                             # within_hours — продолжать только в пределах hours (запись в салон),
  # hours: 24                #   потом сценарий закрывается как «не закончено», новый начинается с нуля
cancel:
  description: …             # из старого disable_prompt
actions:
  - on: completed            # field_filled | field_stuck | all_fields | confirmed | completed | cancelled | abandoned | silence
    do: http_post
    endpoint: results_api
  - on: silence
    after_minutes: 15
    do: http_post
    endpoint: results_api
    status: incomplete
```

Старые сценарии (`docs/legacy-prompts/scripts/*.json`) переводятся в этот формат вручную на этапе 6:
- `steps_order` → `ask_after`;
- `check_prompt` → `filters`;
- `disable_prompt` → `cancel.description`;
- `call_to_action_prompt` → первый стартовый вопрос с весом, равным порогу.

## 5. Ход диалога (`core/turn.py`)

```
вход: сообщение клиента
 → сохранить в messages (повтор того же external_id молча отбрасывается)
 → HTTP: ход сразу; Instagram: задача run_turn с run_at = сейчас + пауза склейки
   (каждое новое сообщение переносит run_at, но не дальше max_wait от первого)

run_turn(conversation_id):
  ВЗЯТЬ (короткая транзакция): аренда диалога; необработанным сообщениям проставить turn_id;
        прочитать состояние и state_version
  --- дальше вызовы LLM вне транзакции ---
  0. pending = эти сообщения → один текст
  1. rewrite      LLM, промпт context_manager_question + правила из context_manager.txt
                  (сленг, несколько вопросов в одном сообщении, ответ на шаг сценария не трогать, язык)
                  вход: dialogue, selected_line, answer_language
  2. route        одна пачка вопросов = один запрос к Jev. Текст клиента — переписанный; если переписанный
                  вышел короче исходного, сообщение — слова клиента целиком, а переписанный идёт
                  следом как пересказ (2026-10-22). История сообщений в маршрут не идёт.
                  Состояние: переписанный текст + сценарии и состояния их полей (без истории):
                  service_type (choice: none / greeting_only / goodbye_only / not_a_bot / ethical_violation)
                  wants_human (boolean)
                  start:<scenario>.<key> (boolean) — стартовые вопросы всех сценариев, кроме того,
                    что в фокусе; голоса считает scenarios/start.py (см. «Запуск сценария» ниже)
                  stop (choice: none / pause_focus / cancel:<run> для любого открытого сценария)
                  change_field (choice: none / заполненные поля в фокусе) — клиент исправляет прошлый ответ
                  search (choice: none / knowledge / catalog) — с этапа 5
                  field:<scenario>.<field> (boolean «в сообщении есть ответ на вопрос поля?»)
                    — все незаполненные поля сценария в фокусе
                    — поля, на которые ссылаются стартовые вопросы (`field: …`) других сценариев
                  → Route (сценарий в фокусе получает приоритет: новые встают на паузу)
  3. scenarios    применить Route: начать / отменить / поставить на паузу / сменить фокус;
                  извлечь значения отмеченных полей (LLM по ИСХОДНОМУ тексту, словами клиента;
                    переписанный идёт подсказкой — где искать). Значение не нашлось в словах
                    клиента → поле не заполняется, бот его спросит; случай пишется в trace;
                  фильтры этих полей — вторая пачка = второй запрос к Jev;
                  цикл перепроверки: поля с needs_recheck, у которых выполнен ask_after,
                    проверяются фильтрами сразу, без вопроса клиенту, пока что-то меняется;
                  выбрать следующий вопрос
  4. data         только то, что нужно Route (этап 5+); поиск — по ПЕРЕПИСАННОМУ тексту
  5. respond      план ответа RespondPlan — чистая функция, без LLM (тестируется на фейках):
                    {ответить_на: вопрос клиента | null, затем: следующее поле | переспрос (фильтры) | ничего}
                  LLM (system_prompt + user_prompt) только формулирует текст по этому плану;
                  вопрос не по сценарию → ответ + в том же сообщении возврат к следующему вопросу
                  режим оператора → 3–4 варианта (этап 4)
  ЗАПИСАТЬ (короткая транзакция, только если аренда всё ещё наша):
        если пришли новые сообщения, а ответ ещё не отправлен → ответ отбросить (dropped),
          ход запустить заново, не больше 2 раз подряд (только Instagram; в HTTP каждый запрос — свой ход);
        иначе: состояние сценариев, ответ (messages pending + задача send_message),
          события field_filled / all_fields / completed / cancelled → actions → jobs,
          перенос таймеров тишины и истечения, trace (turn + llm_calls + decisions), state_version+1;
        снять аренду
```

**Вопросы маршрута — зачем каждый (шаг 2):**

| Вопрос | Что решает | Почему отдельный вопрос |
|---|---|---|
| `service_type` | Служебное сообщение: привет, пока, «ты бот?», недопустимое | На такие сообщения бот отвечает без сценария и поиска. Типы — из старого бота (`_cm_types_table.md`) |
| `wants_human` | Клиент просит живого человека (да/нет) | Бывает вместе с другим запросом: «позовите менеджера, хочу записаться» |
| `start:<сценарий>.<вопрос>` | Признаки, что клиент хочет этот сценарий («хочет записаться?», «назвал услугу?») | По одному «да/нет» на признак: Jev на таких вопросах точнее всего, видно, какие признаки сработали, два сценария могут запуститься сразу. Заменяет один вопрос-выбор «какой сценарий» из прошлой версии плана |
| `stop` | Пауза текущего или отмена любого открытого | В одном сообщении бывает и отмена, и старт: «не надо стрижку, лучше маникюр» |
| `change_field` | Клиент исправляет уже данный ответ: «не в 10, а в 11» | `field:*` спрашивает только про незаполненные поля, без этого исправление потеряется |
| `search` | Нужен ли поиск: база знаний / каталог | Ищем только когда нужно (минимум работы) |
| `field:<сценарий>.<поле>` | Есть ли в сообщении ответ на это поле | Ранние ответы; у сценария не в фокусе этот же ответ идёт голосом в его запуск (`field: …` в `start`) |

**Запуск сценария (решено: «да/нет» с весами; `scenarios/start.py` — чистая функция):**
- У сценария несколько стартовых вопросов. Каждый — свой текст (`ask`) или ссылка на поле (`field: niche` = «в сообщении есть ответ про нишу?»). У каждого вес, по умолчанию 1.
- Ответ «да» — вероятность от Jev 0.5 и выше. Неуверенные вопросы, как и везде, перепроверяет LLM.
- **Сценарий сработал**, когда сумма весов ответов «да» ≥ `threshold`. Примеры для записи (`wants_booking` вес 2, `service` и `datetime` по 1, порог 2):
  - «хочу записаться» → 2 → старт;
  - «на маникюр в пятницу есть окошко?» → 1 + 1 = 2 → старт;
  - «сколько стоит маникюр?» → только услуга = 1 → не старт, бот просто отвечает.
- **Проверка при сохранении:** порог больше суммы всех весов → сценарий никогда не запустится → ошибка. Один вопрос без порога → порог = его вес.
- **Сработало несколько или уже есть фокус:**
  - сценарий в фокусе остаётся в фокусе, новые встают на паузу; бот перейдёт к ним, когда текущий закончится;
  - если `stop` в этом же сообщении поставил текущий на паузу или отменил его («не надо стрижку, лучше маникюр») — фокус переходит к сработавшему;
  - фокуса нет → его получает сценарий с наибольшей суммой; при равенстве — тот, что выше в списке сценариев в админке;
  - сработал сценарий, который уже открыт на паузе, → второй не создаётся; если фокус свободен, он переходит в фокус.
- В `decisions` пишется каждый голос, а в trace хода — сумма по каждому сценарию. В админке видно, почему сценарий запустился или нет.

- **Одна пачка** — это вопросы маршрута, а не контекст-менеджер (контекст-менеджер — отдельный вызов LLM на шаге 1, до маршрута). Jev на Vercel принимает пачку: все вопросы маршрута — один запрос `/v1/evaluate`, Jev отвечает на них за один проход. Как устроен запрос — ниже, «Jev».
- **Переписанный текст** — он самодостаточный («да» уже раскрыто в «да, хочу записаться на маникюр»), и контекст Jev (32k) экономится.
- **Слова клиента — когда переписанный короче (2026-10-22).** Риск, за которым следили, случился: переписывание сделано под поиск и сокращает сообщение («только суть»). Длинный рассказ (39 000 знаков, документ целиком) оно свело к одной фразе в 170 знаков, и маршрут отметил одно поле из всех. Поэтому, если переписанный текст вышел короче исходного, в состоянии маршрута «Client's latest message» — слова клиента целиком, а переписанный идёт следом как «The same message retold with the context of the dialogue». Именно в таком порядке: все вопросы маршрута спрашивают про «последнее сообщение клиента», и когда под этим заголовком стоял пересказ, а слова клиента шли вторым блоком, Jev их почти не читал (живой прогон на том же тексте: 4 поля из 41; со словами клиента под заголовком — 17). Короткий ответ («да» → «да, хочу записаться на маникюр») переписанный удлиняет, и там всё как раньше. В trace хода у шага route тогда стоит `own_words: true`.
- **Потолка у текста клиента нет, и он не режется (2026-10-22).** Весь запрос к Jev — состояние, все вопросы пачки и обёртка Jev — не больше 32k токенов: это окно модели. Gateway принимает и длиннее и отвечает (маршрут рассказа на 39 000 знаков ушёл одним запросом в 36 751 токен), поэтому предел держим сами. Сообщение, которое не влезает рядом с вопросами, делится на части по абзацам, затем строкам, предложениям, словам (`state_render.render_route_parts`): каждая часть — отдельный запрос со всеми вопросами («Client's latest message, part i of n»), части уходят одновременно. Разделы сценариев идут с каждой частью (не меньше половины части, лишнее режется с конца); пересказ — с каждой частью, если он не длиннее четверти места, иначе своими частями. Ответы частей сводятся (`engine.merge_parts`):
  - уверенный не нейтральный ответ хоть в одной части — ответ всего сообщения: «да» в одной части = «да», «стоп» и «исправляю ответ» засчитываются в любой части; из нескольких — самый уверенный;
  - иначе неуверенный ответ хоть в одной части делает неуверенным всё;
  - иначе нейтральный ответ (у «да/нет» — «нет», у выбора — вариант `neutral` вопроса) с наименьшей уверенностью;
  - варианты, которые описывают сообщение целиком (`whole_only`: «просто приветствие», «просто прощание», «кто ты»), в части не засчитываются: часть длинного сообщения — не приветствие. «Неэтичная просьба» в части засчитывается.

  В журнале решений пишутся ответы всех частей и их цена; `used` — только у ответа, который взят. В trace хода у шага — `parts`.

**Jev (`decisions/jev_decider.py`):**
- **Основной решатель — Jev, с этапа 1.** `LLMDecider` (OpenAI) — запасной: неуверенные ответы и сбои Jev. Ещё он нужен для сравнения в теневом режиме (этап 7).
- **Запрос** `POST https://ai-gateway.vercel.sh/v1/evaluate`, заголовок `Authorization: Bearer $AI_GATEWAY_API_KEY`:
  ```json
  {"model": "typesafe-ai/jev",
   "state": "<компактное состояние из state_render.py>",
   "questions": {
     "wants_human":  {"type": "boolean", "instructions": "…",
                      "criteria": {"true": "…", "false": "…"}},
     "start:booking.wants_booking": {"type": "boolean", "instructions": "…",
                      "criteria": {"true": "…", "false": "…"}},
     "service_type": {"type": "choice", "instructions": "…",
                      "criteria": {"none": "…", "greeting_only": "…", "not_a_bot": "…"}}},
   "providerOptions": {"gateway": {"zeroDataRetention": true, "only": ["typesafe-ai"]}}}
  ```
  Ответ: `answers.<ключ>`. У boolean — `probability`; у choice — `choice` и `probabilities`; у score — `score` и `probabilities`. Плюс `usage` и `providerMetadata.gateway` (`cost`, `generationId`).
- **Типы:** наш «да/нет» → `boolean`; выбор → `choice` (вариант = ключ в `criteria`, значение — описание варианта); оценка → `score` (пока не нужен).
- **Уверенность** — одно число от 0 до 1 для порога и журнала:
  - boolean — max(p, 1−p): p = 0.98 и p = 0.02 одинаково уверенные, p = 0.5 — полная неуверенность;
  - choice — вероятность выбранного варианта;
  - score — вероятность самой вероятной ступени.
- **Лимиты** (`decisions/limits.py`):
  - весь запрос — состояние, все вопросы и обёртка Jev (около 300 токенов) — не больше 32k токенов;
  - в choice — не больше 255 вариантов, в score — не больше 10 ступеней.

  Токены оцениваются, а не считаются: кириллическая буква — 0,9 токена, прочий ASCII — 0,3, остальное — 1,5. Замер на Jev (`scripts/jev_tokens.py`, 8 000 знаков текста): английский — 1 933 токена (4,1 знака на токен), русский — 4 349 (1,8), украинский — 5 676 (1,4). Оценка выше реального счёта на всех замерах: на украинском на 7 %, на настоящих запросах диалога на 19–24 %. Прежняя оценка (знаки ÷ 3) недосчитывала кириллицу в 2–2,5 раза.

  Сообщение, которое не влезает рядом с вопросами, делит на части вызывающий (маршрут, проверки ответов, поиск); место под часть — не меньше половины окна. Если вопросы и с такой частью не влезают в один запрос, `JevDecider` делит пачку на несколько запросов и шлёт их параллельно.
- **Проверки ответов** (`scenarios/checks.py`). Пока всё влезает — одно состояние, как раньше. Иначе: ответы под проверкой — столько запросов, сколько нужно, к ним принятые ответы как контекст (до четверти окна, обрезаются с конца); ответ, который один не влезает в запрос, — частями, фильтр пройден, если прошла хоть одна часть. Вопросы «когда задавать вопрос» (`show_if`) — отдельным запросом с карточкой диалога целиком; карточка длиннее окна не режется, вопрос не задаётся (`shows_dropped`), как раньше. Отказ `check.too_long` у `POST /v1/scenarios/{key}/check` и запуска с ответами убран: длинные ответы проверяются частями.
- **Поиск** (`search/service.refine`): запрос клиента длиннее окна — частями, кандидат подходит, если подошёл хоть в одной части.
- **Ниже порога:** только неуверенные вопросы заново уходят в `LLMDecider`, одним вызовом. Встроенную резервную модель Gateway (`providerOptions.gateway.models` с условием `when`) не берём: она повторяет ВЕСЬ запрос на другой модели, то есть платим за всё дважды и ждём дольше.
- **Ошибки:**
  - 400 — ошибка в нашем запросе: без повторов, запись в журнал, громкий лог;
  - 500, 502, сеть, таймаут — 1 повтор, потом вся пачка уходит в `LLMDecider` (в журнале `reason=jev_error`).

  Ход из-за Jev не падает.
- **Цена и логи:** `cost` и `generationId` из ответа пишутся в `decisions`. По `generationId` запрос находится в логах Vercel.
- **Чего Jev не делает:** не извлекает значения. На числах, датах, телефонах и суммах он слаб (docs/02). Извлечение — LLM, с этапа 6 — код. Jev отвечает только на вопросы «да/нет» и «какой вариант».
- **Данные клиентов:** `zeroDataRetention: true` — просим Gateway не хранить тексты запросов. Что запрос с этим флагом проходит, проверяем на пробе.

**Модели LLM (`llm/registry.py`) — заводит админ, в коде нет ни одной (решено):**
- **Модель** — запись в `llm_models`: имя у Gateway (`openai/gpt-6-luna`), цены, окно контекста, что умеет.
- **Роль** — задача, для которой нужна модель. Список ролей задаёт код (их вызывает ход), а какая модель на роли — решает админ:
  - `reply` — ответ клиенту и 3–4 варианта оператору;
  - `rewrite` — контекст-менеджер (переписывание вопроса);
  - `extract` — извлечение значений полей;
  - `decide` — запасной решатель вместо Jev;
  - `vision` — чтение чеков (этап 6);
  - `embed` — эмбеддинги (этап 5). Смена модели = переиндексация всего каталога и базы знаний, админка предупреждает и ставит задачу.
- **Настройка роли** (`model_roles`): модель, `reasoning_effort`, таймаут, запасная модель (если основная не ответила после повторов). Есть общая настройка и своя у тенанта, своя важнее.
- **Переключение — сразу:** настройка роли читается из БД в начале каждого хода (один маленький запрос), перезапуск не нужен. Кто и когда сменил модель — в `audit_log`.
- **Добавить модель быстро:** админка показывает каталог Gateway (`GET /v1/models`, там есть цены), админ выбирает модель — цены и окно контекста подставляются сами, их можно поправить. Кнопка «Проверить» делает тестовый вызов перед сохранением.
- **Защита от ошибок:**
  - роли не назначена модель → ход не идёт, понятная ошибка в журнале и красная плашка в админке («роли `reply` не назначена модель»);
  - модель, которая стоит на какой-то роли, выключить или удалить нельзя;
  - роли нужна схема JSON (`rewrite`, `extract`, `decide`), а модель её не умеет → сохранить нельзя.
- **В коде и `.env` остаются только единичные внешние вещи:** адрес и ключ Gateway, имя Jev (`typesafe-ai/jev`).

**Правила сценария (`scenarios/runtime.py`):**
- **Следующее поле** — первое по порядку из описания, которое не заполнено и у которого все поля из `ask_after` заполнены. Частично заполненное поле и поле с `needs_recheck` считаются незаполненными.
- **Ранний ответ:** поле заполнено раньше своей очереди → `needs_recheck = true`. Как только его `ask_after` выполнен, в том же ходе фильтры прогоняются ещё раз, уже с контекстом. Прошли — поле засчитано, клиента не спрашиваем. Не прошли — поле становится частичным, бот переспрашивает.
- **Исправление:** клиент поменял уже заполненное поле → оно проверяется заново, а все поля, которые от него зависят через `ask_after`, получают `needs_recheck`.
- **Частичный ответ:** новый ответ клиента добавляется к старому, фильтры проверяются заново.
- **Переспрос:** в `respond` передаются вопрос поля, частичный ответ и тексты непройденных фильтров. LLM строит уточняющий вопрос и формулирует его каждый раз по-новому.
- **Лимита попыток нет.** Выходы только три: отмена, тишина, оператор. Защита от ошибок решающей модели (Jev или LLM): если одно поле переспрошено 3 раза подряд, оно помечается `stuck`. Это видно в админке и запускает событие `field_stuck`, на которое можно повесить уведомление или передачу оператору. Бот при этом продолжает спрашивать.
- **Фокус:** один сценарий. Когда он завершился, в фокус сразу переходит следующий на паузе (самый недавний). Сценарий на паузе тоже принимает данные и его тоже можно отменить.
- **Завершение** по `completion`. При `all_fields` сценарий завершается, когда все поля заполнены и ни у одного нет `needs_recheck`.
- **Отмена после частичной отправки:** если по сценарию уже ушёл частичный JSON, при отмене уходит ещё один со статусом `cancelled`.
- **Клиент ушёл в сторону** (решено): бот отвечает на вопрос и в том же сообщении возвращает к следующему вопросу сценария.
- **Возврат после паузы** (решено): правило `resume` задаётся в самом сценарии. При `within_hours` срок продлевается каждым ходом (задача `expire:<run_id>`). Если срок вышел, сценарий получает статус «не закончено» (`abandoned`), во внешний API уходит финальный JSON с этим статусом, а при следующем запросе клиента начинается новый запуск.
- **Тишина** только отправляет частичный JSON и ничего не закрывает. Перед отправкой задача берёт аренду диалога и заново проверяет `last_client_at`: если клиент успел написать, отправка не нужна.

**Языки:**
- **Список языков и правило ответа — в настройках тенанта** (решено):
  ```yaml
  languages: [uk, en]     # на каких языках бот отвечает; на них же пишутся сценарии
  reply_language:         # язык клиента → язык ответа (принудительно)
    uk: uk
    ru: uk                # на русский отвечаем по-украински
    "*": en               # все остальные языки → английский
  ```
  - Без правила для языка: если язык клиента есть в `languages` — отвечаем на нём, иначе на первом языке из списка.
  - Каждый язык справа в правиле обязан быть в `languages` — проверяется при сохранении.
- **В диалоге два языка:** `conversations.client_language` (на каком пишет клиент) и `conversations.reply_language` (на каком отвечает бот, по правилу выше).
- **Язык клиента** определяет LLM на шаге rewrite: это поле уже есть в старом `context_manager.txt`, LLM видит весь диалог и отличает украинский от русского и суржика лучше, чем детектор по одному сообщению. Отдельный детектор (lingua) не нужен.
- **Короткое сообщение язык не меняет.** «ок», «+», «так», эмодзи, номер телефона → язык остаётся прежним. Первое сообщение без явного языка → первый язык из `languages`.
- **Ответ** всегда на `reply_language`: он передаётся как `answer_language` в rewrite и в respond, как в старом боте.
- **Переписанный вопрос — тоже на `reply_language`.** Маршрут и проверки полей работают только с переписанным текстом, значит Jev и проверки видят только языки тенанта (uk, en), а не любой язык клиента.
- **Один сценарий — один файл для всех языков тенанта.** Отдельные копии сценария под каждый язык не нужны.
  - Любой текст в сценарии (вопрос поля, проверка, стартовый вопрос, описание отмены) — словарь «язык → текст» (`{uk: …, en: …}`) или просто строка, если у тенанта один язык. В pydantic это один тип `LocalizedText`.
  - Бот берёт текст на `reply_language`. Вопрос поля — подсказка для LLM: она формулирует его каждый раз сама, опираясь на этот текст.
  - Нет текста на каком-то языке тенанта → сценарий сохраняется, но админка показывает предупреждение. В работе LLM переводит с основного языка сценария (поле `language` в YAML).
- **Проверки полей (вопросы Jev)** — тексты на языках тенанта, как и вопросы. Как Jev справляется с украинским и на каком языке лучше писать ему вопросы (uk или en), выясняем пробой на этапе 0 (docs/03 §14, вопрос 6). Если en заметно точнее — служебные вопросы маршрута пишем по-английски, а фильтры полей остаются на языках тенанта.
- **Значения полей** сохраняются словами клиента, на его языке, без перевода (решено). В JSON результата — `client_language` и `reply_language`.
- **Поиск** (этап 5):
  - Qdrant (смысловой поиск): эмбеддинги OpenAI `text-embedding-3-large` многоязычные, поэтому вопрос на любом языке находит текст на другом;
  - ES (поиск по словам) работает на языке, на котором написан каталог: для uk / ru / en — свои анализаторы (правила разбора слов), для остальных — общий ICU;
  - ищем по переписанному вопросу, а он уже на `reply_language` (одном из языков тенанта), поэтому ES ищет на том же языке, на котором ведётся каталог;
  - база знаний сначала ищется на `reply_language`, если ничего не нашлось — на любом языке тенанта.
- **Админка** — многоязычная (решено): на старте английский, украинский, русский, потом список расширяется. Язык интерфейса админки — отдельная настройка пользователя (`users.locale`), он не связан с языками бота у тенанта (`languages`). Подробно — этап 3.

**Надёжность хода:**
- входящее сообщение сначала сохраняется, ход идёт потом. Вебхук Instagram только сохраняет и ставит задачу, отвечает Meta сразу;
- повтор одного сообщения от Meta отсекается по `messages.external_id` (mid). В `POST /v1/messages` для того же есть `client_message_id`;
- ответ в Instagram отправляется задачей `send_message` с повторами. `mid`, который вернул Graph API, сохраняется в `external_id`;
- **echo** (Meta присылает копию каждого исходящего сообщения, в том числе ответов бота): если `mid` уже есть в `messages`, это наш ответ, пропускаем. Если нет — оператор написал прямо из приложения Instagram. Echo обрабатывается с задержкой в несколько секунд, чтобы `mid` нашего ответа успел сохраниться;
- события сценария и задачи (отправка, тишина, истечение) пишутся в одной транзакции.

**Отправка результата (`results/delivery.py`):**
- `POST` на `endpoint.url`, тело — JSON по образцу из `docs/03-plan.md` §7.3;
- заголовки: `Idempotency-Key: <delivery_id>` (защита от дублей) и `X-Zama-Signature: sha256=HMAC(secret, body)` (подтверждает, что прислали мы);
- **2xx** — отправлено;
- **4xx** (кроме 408 и 429) — ошибка сразу, без повторов;
- **5xx и сеть** — повторы через 1 мин, 5 мин, 30 мин, 2 ч, 6 ч, потом «ошибка», видно в админке;
- **тишина:** задача `silence_check:<run_id>` переносится на каждом ходу. Сработала → отправка со статусом `incomplete`. Клиент вернулся → сценарий продолжается, в конце уходит отправка с тем же `result_id` и статусом `completed`;
- **порядок версий:** в JSON есть `seq` (номер версии результата, растёт с каждой отправкой). Новая отправка того же результата на тот же адрес отменяет ещё не прошедшие повторы старых. Иначе повтор частичного JSON через 6 часов пришёл бы позже полного и затёр его.

## 6. Этапы

Каждый этап — набор небольших коммитов. В конце этапа: `make lint test` зелёные и пройдена ручная проверка из «готово, когда».

### Этап 0. Каркас

1. `docker-compose.yml` (postgres), `Makefile`, `pyproject.toml`, ruff, pytest, `.gitignore` (`tmp/`, `.env`, `secrets/`), `.env.example` (`AI_GATEWAY_API_KEY=`, `AI_GATEWAY_URL=https://ai-gateway.vercel.sh/v1`).
2. `settings.py`, `db/`, Alembic. Первая миграция: tenants, channels, api_keys, contacts, conversations, messages, turns, llm_calls, llm_models, model_roles, jobs. `create-tenant` сразу создаёт канал kind=http, `create-api-key` привязывает ключ к нему.
3. LLM-сервис `llm/service.py`: `complete()` поверх OpenAI SDK (`base_url` = Vercel AI Gateway), таймауты, 2 повтора, подсчёт токенов и цены, запись в `llm_calls` (с `generation_id`). В старом боте таймаутов и повторов не было.
   - `complete()` принимает **роль**, а не модель. Модель, `reasoning_effort`, таймаут и запасную модель берёт `llm/registry.py` из `model_roles` (§5 «Модели LLM»). Имён моделей в коде нет.
   - Структурированный ответ — `response_format` json_schema.
   - Цена — из ответа Gateway, иначе по ценам из `llm_models`.
4. Очередь задач: `jobs/queue.py`, `worker.py`. Повторы с паузой, перенос по `dedupe_key`. `worker.run_due(now)` — выполнить всё, что созрело к моменту `now` (для тестов с ручными часами).
5. `core/clock.py` — `Clock`; `core/lease.py` — аренда диалога (взять / продлить / проверить / снять).
6. `POST /v1/messages` (ключ `Authorization: Bearer <api_key>`). Тело: `{contact: {external_id, name?}, text, client_message_id?}` → ответ `{conversation_id, turn_id, reply}`. Повтор с тем же `client_message_id` возвращает тот же ответ. Плюс `POST /v1/conversations/history`.
7. `run_turn` пока в простом виде, но уже в форме «взять → LLM → записать»: история → LLM → ответ. Задача `send_message` (outbox) — заготовка под каналы.
8. CLI: `create-tenant`, `create-api-key`; модели до появления админки:
   - `zama models add openai/gpt-6-luna --from-gateway` — цены и окно контекста подтягиваются из каталога Gateway;
   - `zama models assign reply openai/gpt-6-luna` (или `--role '*'` — на все роли сразу);
   - `zama models list` — модели и кто на какой роли.

   Пишут в те же таблицы, что потом правит админка.
9. **Проба Jev** — `backend/scripts/jev_probe.py`, запуск `make jev-probe`. Цель: до этапа 1 узнать, как Jev работает на наших языках, и выставить начальные пороги.
   - набор: около 30 уже переписанных фраз на uk / ru / en (из старых диалогов Zama Salon и придуманные) с правильными ответами. Набросок делаю я, **пользователь проверяет правильные ответы**;
   - вопросы: `service_type`, `wants_human`, стартовые вопросы интервью и записи (`start:*`, «да/нет») и 2–3 фильтра интервью;
   - каждый вопрос в двух вариантах — `instructions` и `criteria` на uk и на en. Так выясняем, на каком языке писать вопросы Jev;
   - тот же набор через LLM-модель в том же `/v1/evaluate` (Gateway пишет, что языковую модель можно поставить в `model`; имя модели — параметр пробы, на пробе `openai/gpt-6-luna`). Если работает — `LLMDecider` шлёт тот же запрос с моделью своей роли, и отдельный промпт со схемой JSON не нужен;
   - заодно проверить: лимиты, флаг `zeroDataRetention`, какие ключи вариантов choice допустимы, проходит ли `reasoning_effort` в chat completions через Gateway;
   - отчёт `tmp/jev-probe/report.md`: точность по языкам, уверенность на ошибках (ошибается ли Jev уверенно), время, цена. Вся проба стоит доли цента.

**Тесты:**
- очередь: захват задачи, повтор, перенос, два воркера не берут одну задачу;
- аренда: второй ход ждёт; истёкшая аренда забирается; запись с чужой арендой отклоняется;
- LLM-сервис на фейковом HTTP: модель берётся из настройки роли; своя настройка тенанта важнее общей; роль без модели → понятная ошибка; основная модель не ответила → запасная;
- API-ключ: чужой и отозванный ключи не проходят; повтор `client_message_id`.

Аренда и `SKIP LOCKED` проверяются **только на настоящем Postgres** с отдельными соединениями, без отката транзакции в фикстуре (иначе тест ничего не проверяет).

**Готово, когда:** после `zama models add` / `assign` `curl` на `/v1/messages` получает ответ LLM, а в БД записаны messages, turns, llm_calls и цена. Отчёт пробы Jev лежит в `tmp/jev-probe/`, и по нему решено, на каком языке писать вопросы Jev.

### Этап 1. Ядро хода

1. `prompts/`: таблица с версиями. `zama seed-prompts` загружает `docs/legacy-prompts/*.txt` как общие промпты. `render.py` подставляет `%…%` и поля JSON.
2. `core/rewrite.py` — переписывание по `context_manager_question` + правила из `context_manager.txt` (сленг, несколько вопросов, ответ на шаг сценария не трогать, язык), как договорено в docs/03 §4. Вход: `dialogue` = сообщения без system, `selected_line`, `answer_language`. Из ответа берём `question` и `language`, поле `role` пока игнорируем.
3. `core/language.py` — языки диалога (§5 «Языки»): язык клиента из rewrite (короткое или нейтральное сообщение его не меняет) → `reply_language` по правилу тенанта. Без lingua.
4. `decisions/`: `Question`, `Decision`, `Decider`.
   - `JevDecider` — основной, по §5 «Jev»: типы, уверенность, деление пачки по лимитам, повтор, переход на LLM при сбое.
   - `LLMDecider` — запасной. Если проба подтвердила, что Gateway принимает языковую модель в `/v1/evaluate`, — тот же запрос, в `model` — модель роли `decide`. Если нет — одна пачка вопросов в один вызов со схемой JSON, уверенность модель пишет сама.
   - `policy.py`: по ключу вопроса — порог (начальные значения — из отчёта пробы) и что делать ниже порога (на этом этапе — спросить LLM).
   - Журнал `decisions`: каждый ответ с провайдером, причиной (`primary` / `below_threshold` / `jev_error`), ценой и `generation_id`.
   - `FakeDecider` для тестов — строгий: ответы задаются правилами по ключам вопросов, на вопрос без правила тест падает.
5. `core/state_render.py` — компактное состояние для маршрута: переписанный вопрос, сценарии и состояния полей. Без исходного текста и без истории сообщений. Ограничение по токенам.
6. `core/routing.py` — вопросы `service_type`, `wants_human` (стартовых вопросов пока нет: сценарии появятся на этапе 2). Ответы на служебные типы — по старым `scripts/2,3,4,5_*.json`.
7. `core/respond.py` — старые `system_prompt` + `user_prompt` (`client_description` из настроек тенанта, `context` пока пустой).
8. `wants_human` → флаг `handover` в ответе и в диалоге (реальная передача — этап 4).
9. Трасса хода в `turns.trace`: этапы, время, ссылки на llm_calls и decisions.

**Тесты:**
- рендер промптов;
- `JevDecider` на фейковом HTTP: разбор boolean / choice / score и расчёт уверенности; пачка больше лимита делится на несколько запросов; 400 → без повтора; 502 → повтор → `LLMDecider`; ниже порога в LLM уходят только неуверенные вопросы; ключ не попадает в логи;
- `LLMDecider` на фейковом LLM: разбор ответа, битый JSON → повтор → ошибка в журнал;
- маршрут: «привет» → greeting_only, «ты бот?» → not_a_bot; в состояние маршрута попадает переписанный текст; когда он короче исходного — исходный целиком, а переписанный следом;
- язык (правило ru, uk → uk; остальные → en): клиент пишет по-русски → ответ по-украински; по-немецки → по-английски; «ок» язык не меняет; правило со ссылкой на язык не из `languages` не сохраняется;
- `tests/dialogs/` — первые диалоги в YAML на фейках.

**Готово, когда:** у любого хода по `turn_id` видно исходный текст, переписанный вопрос, все решения с уверенностью и провайдером (jev / llm), промпт и ответ, цену. «Привет» и «позовите менеджера» на живом Jev дают правильный маршрут.

### Этап 2. Сценарии на примере интервью

1. `scenarios/schema.py` (формат §4), `loader.py`, `zama load-scenarios scenarios/ [--channel <id>]` (загруженные сценарии включаются в указанном канале). Миграция: scenarios, scenario_runs, channel_scenarios, endpoints, deliveries.
2. `scenarios/offer_interview.yaml` — набросок полей и фильтров. **Пользователь проверяет формулировки до запуска.**
3. `runtime.py` + `fields.py`: статусы, фокус и пауза, следующее поле, `ask_after`, ранний ответ и цикл перепроверки, исправление поля, частичный ответ и слияние, `stuck`, `resume` и `expire`.
4. Маршрут: стартовые вопросы `start:<scenario>.<key>`, `stop`, `change_field`, `field:<scenario>.<field>`. `scenarios/start.py` считает сумму весов и решает, кто получает фокус (§5 «Запуск сценария»). Проверка `start` при загрузке: порог ≤ суммы весов, `field:` ссылается на существующее поле.
5. `extract.py`: значение для отмеченных полей. LLM по мотивам `check_script_answers`, по исходному тексту клиента, только его слова, без пересказа.
6. `checks.py`: вторая пачка — фильтры отмеченных полей.
7. `respond.py`: `RespondPlan` (чистая функция) + формулировка через LLM: следующий вопрос, переспрос по непройденным фильтрам, «ответить и вернуть», варианты для поля с выбором.
8. `actions/`: реестр + `http_post`. `results/delivery.py` по §5.
9. Таймер тишины (с проверкой аренды и `last_client_at`), задача истечения для `resume: within_hours`, повторная отправка с тем же `result_id` и новым `seq`.
10. `api/dev.py`: `POST /dev/sink/{name}` сохраняет пришедший JSON и показывает его, чтобы проверять без внешнего сервиса.

**Тесты (основная масса — здесь):**
- `fields`/`runtime`: порядок, `ask_after`; ранний ответ (прошёл → перепроверка без вопроса клиенту; не прошёл → переспрос); исправление поля сбрасывает зависимые; частичный + дополнение; `stuck` после 3 переспросов; отмена сценария в фокусе и на паузе; два сценария (фокус → завершение → следующий на паузе); одно поле в двух сценариях;
- `start.py`: «2 из 3» (веса 1, порог 2) — два «да» запускают, одно нет; вес = порогу — запуск одним признаком; порог больше суммы весов — ошибка при загрузке; сработали два сценария без фокуса → фокус у большей суммы, при равенстве — у первого по порядку; при занятом фокусе новый встаёт на паузу; `stop` + старт в одном сообщении → фокус переходит; сработал уже открытый на паузе → второй не создаётся;
- `RespondPlan`: вопрос не по сценарию → в плане и ответ, и следующий вопрос;
- `LocalizedText`: строка и словарь читаются одинаково; при `reply_language: en` берётся текст `en`, если он есть, иначе текст на основном языке + перевод LLM; нет текста на языке тенанта → предупреждение при загрузке;
- `resume`: `always` — продолжаем через неделю; `within_hours` — после срока `abandoned` + финальный JSON, новый запрос начинает новый запуск;
- delivery: подпись, повторы по 5xx, нет повторов по 4xx, один `result_id` при повторной отправке, старая частичная отправка не затирает новую, отправка не теряется при падении между ходом и отправкой;
- диалоги YAML: полное интервью; интервью клиента на русском при правиле ru → uk (вопросы по-украински, значения полей словами клиента по-русски, в JSON `client_language: ru`, `reply_language: uk`); интервью с ранними ответами; уход в сторону и возврат; клиент замолчал → частичный JSON → вернулся → полный JSON.

Все таймеры в тестах — через ручные часы и `worker.run_due(now)`, без реального ожидания.

**Ручная проверка на реальной LLM:** `make eval` прогоняет 5–10 записанных разговоров интервью. Отчёт кладётся в `tmp/eval/`: где переспросил, где пропустил, итоговый JSON. Параметры `MODEL_<РОЛЬ>=…` и `EFFORT=…` прогоняют те же разговоры с другой моделью или другим уровнем размышления (только на этот прогон, настройки в БД не меняются). В отчёте время и цена хода по каждой роли, чтобы выбрать модель и уровень по скорости и качеству.

**Готово, когда:** интервью проходит целиком, JSON приходит в `/dev/sink`, через 15 минут тишины приходит частичный JSON.

### Этап 3. Админка v1

**Бэкенд `/v1/admin/*`:**
- **вход без паролей, как в factory** (`factory/api/services/passwordless.py`, `api/routes/auth_email.py`, `frontend/server/api/auth/google*.js`):
  - **Google:** `GET /v1/admin/auth/google/start` → cookie `g_oauth_state` (10 мин, httpOnly, sameSite lax) → редирект на Google (`openid email profile`, `prompt=select_account`); `GET …/google/callback` сверяет state, меняет код на токен **на бэкенде** (секрет только там), берёт email и `sub`;
  - **Ссылка на почту:** `POST /v1/admin/auth/magic-link` — email в нижний регистр, не чаще 1 раза в минуту на адрес; токен `secrets.token_urlsafe(48)`, в БД только sha256, живёт 15 мин, одноразовый; письмо через SMTP (`SMTP_HOST/PORT/USER/PASSWORD/FROM/FROM_NAME/USE_TLS`), тексты en / uk / ru, кнопка в стиле factory; ответ всегда `{ok: true}` (нельзя узнать, есть ли такой адрес); `MAGIC_LINK_DEV_ECHO=1` — в dev ссылка в ответе и в логе. `POST …/magic-link/verify` → сессия или код `auth.link_expired` / `auth.bad_token`;
  - **войти может только уже заведённый пользователь** (приглашённый админом или созданный `zama create-user --superadmin`); Google-вход привязывает `google_sub` при первом входе;
  - сессия — таблица `sessions` (в БД хеш токена) + httpOnly-cookie `zama_session`, 30 дней, продлевается; `POST …/logout`, `GET …/me`;
  - Nuxt проксирует `/api/**` на бэкенд — cookie получаются «свои» для домена админки;
- роли owner/admin/operator, проверка в `deps.py`;
- `audit_log` — кто что поменял;
- CRUD: тенанты, пользователи, API-ключи, endpoints, промпты (новая версия / откат), сценарии (сохранение с проверкой схемы → новая версия);
- результаты: список, фильтры, «отправить ещё раз»;
- диалоги с трассой ходов;
- песочница: ход без канала, ответ + трасса;
- модели и роли (§5 «Модели LLM»): список, добавление из каталога Gateway, правка цен, «Проверить», назначение модели на роль (общее и для тенанта); расходы по моделям и ролям;
- **ошибки и предупреждения — кодом с параметрами, без готового текста** (например `{"code": "scenario.threshold_too_high", "params": {"threshold": 5, "max": 3}}`). Текст на нужном языке собирает фронт. Так бэкенд не зависит от языков админки.

**Фронт `admin/` (Nuxt SPA) — дашборд как в factory:**
- каркас и стиль берём из `factory/frontend`: `tailwind.config.js` (slate-палитра, primary `#3494E6`, secondary `#EC6EAD`, радиусы card/button/input/modal, шрифты Plus Jakarta Sans / Inter / JetBrains Mono), `layouts/app.vue` + `auth.vue`, `AppSidebar` (группы меню, сворачивание 260↔72px, состояние в localStorage), `AppHeader` (крошки, `LanguageSwitcher`, `ThemeToggle`, `UserMenu`), мобильное меню, `ConfirmDialog`;
- страница входа как `factory/components/auth/LoginForm.vue`: кнопка Google, «или», email → «проверьте почту»; `pages/auth/magic.vue` — подтверждение ссылки;
- `middleware/auth` и `guest`, Pinia-стор пользователя;
- **языки интерфейса** (решено): en, uk, ru.
  - `@nuxtjs/i18n`, все надписи — из файлов `admin/i18n/locales/{en,uk,ru}.json`, в шаблонах текста напрямую нет;
  - новый язык = новый файл + одна строка в настройке, код не меняется;
  - при первом входе язык берётся из браузера (если его нет в списке — английский), потом пользователь выбирает сам, выбор хранится в `users.locale`;
  - даты, числа и суммы — в формате выбранного языка (`Intl`);
  - не переводятся: тексты сценариев и промптов (это содержимое, у него свои языки) и технические ключи (`service_type`, `start:booking.wants_booking`);
- вход;
- результаты;
- диалоги (лента + раскрывающаяся трасса хода);
- редактор сценария: стартовые вопросы (свой текст или ссылка на поле, вес, порог; подсказка «сработает, например, при: …»), поля, фильтры, `ask_after`, действия; у текстов вкладки по языкам тенанта, незаполненный язык подсвечен; рядом JSON для продвинутых;
- сценарии канала: какие включены и в каком порядке (перетаскиванием) — порядок решает, кто получает фокус при равной сумме;
- в трассе хода — какие стартовые признаки сработали и сумма по каждому сценарию;
- настройки тенанта: список языков и правило «язык клиента → язык ответа»;
- промпты с diff версий;
- **модели:** таблица моделей с ценами; «Добавить» — поиск по каталогу Gateway с автоподстановкой цен; «Роли» — у каждой роли выпадающий список моделей, уровень размышления, таймаут, запасная модель; красная плашка, если у роли нет модели; расходы за день и месяц по моделям;
- песочница (можно выбрать модель для пробного хода, не меняя роль);
- настройки.

**Тесты:**
- права по ролям (оператор не может менять сценарии, промпты и модели), версии промптов и сценариев;
- модели: смена модели на роли действует со следующего хода без перезапуска; модель на роли нельзя выключить; роль без модели → понятная ошибка;
- переводы: `make i18n-check` (входит в `make lint`) — во всех языках одинаковый набор ключей, у каждого кода ошибки с бэкенда есть перевод.

**Готово, когда:** новый сценарий собирается в админке и проверяется в песочнице без правки кода; интерфейс переключается между en, uk и ru без перезагрузки.

### Этап 4. Instagram Direct и режим оператора

1. `channels/instagram/`:
   - вебхук: проверка `hub.challenge`, подпись `X-Hub-Signature-256`;
   - разбор сообщений, вложений и echo (ответ, который оператор отправил прямо из приложения Instagram);
   - **канал** определяется по `recipient.id` (наш аккаунт), **клиент** — по `sender.id` (IGSID). Так у каждого клиента свой диалог (в старом боте все клиенты тенанта попадали в одну сессию);
   - отправка: Instagram Login API, `POST https://graph.instagram.com/v23.0/{ig_business_id}/messages`, `Authorization: Bearer <token>`, тело `{"recipient":{"id":…},"message":{"text":…}}`;
   - `channels` с зашифрованным токеном. Токены из старого репозитория засвечены в git — **перед подключением выпустить новые**.
   - **Подключение аккаунта из админки** (кнопка «Подключить Instagram», аккаунтов сколько угодно):
     - одно наше приложение Meta на всю систему: `META_APP_ID`, `META_APP_SECRET`, `IG_WEBHOOK_VERIFY_TOKEN` в env; один адрес вебхука на все аккаунты;
     - вход через Instagram (Instagram Business Login, права `instagram_business_basic` + `instagram_business_manage_messages`) → бэкенд меняет код на токен → долгий токен (60 дней) → сохраняет канал (id, username, аватар) → подписывает аккаунт на вебхук `messages` (`POST /me/subscribed_apps`);
     - задача `refresh_ig_token` продлевает токен заранее; не продлился → статус `error`, красная плашка в админке и уведомление;
     - запасной путь для тестов — вставить токен руками;
     - **ограничение Meta:** пока приложение не прошло проверку Meta (App Review, расширенный доступ к сообщениям), подключить можно только аккаунты, добавленные в приложение тестерами. Для чужих (клиентских) аккаунтов нужна проверка — подать заявку, когда бот заработает на своём аккаунте;
   - **сценарии по аккаунту:** сценарии лежат в библиотеке тенанта, у каждого канала свой набор включённых и свой порядок (`channel_scenarios`). Маршрут видит только сценарии канала этого диалога. Свои языки, описание бизнеса, режим оператора — тоже по каналу (если не заданы — берутся у тенанта).
2. Склейка: `run_turn` с паузой N секунд (настройка канала), новые сообщения переносят ход.
3. 24-часовое окно: `last_client_at`. Вне окна бот не пишет. Ответ оператора — по правилам Meta для «human agent», если он доступен.
4. Режим оператора:
   - `respond` возвращает 3–4 варианта → `operator_tasks(choose_reply)`;
   - выбор / правка → отправка;
   - новое сообщение клиента → пересборка вариантов;
   - echo от оператора → задача снимается.
5. `wants_human` → передача: бот замолкает в этом диалоге, создаётся задача и уведомление.
6. Уведомления: `notify_telegram` (токен бота + список chat id в настройках действия, токен зашифрован; вызов `sendMessage`), `notify_email`. Язык уведомления (en / uk / ru) — настройка действия; шаблоны — `backend/app/actions/templates/<язык>/`, их тоже проверяет `make i18n-check`.
7. Напоминания о сценариях на паузе — только в пределах 24 часов.
8. Админка: раздел «Каналы» (список аккаунтов со статусом, «Подключить Instagram», отключить, у канала — вкладки «Сценарии» (включить/выключить, порядок перетаскиванием), «Языки», «Режим оператора»); очередь оператора (обновление опросом раз в несколько секунд, без сокетов).

**Тесты:** разбор реальных образцов вебхука (сохранить в `tests/fixtures/`), подпись, склейка трёх сообщений в один ход, правила окна, пересборка и снятие вариантов.

**Готово, когда:** на тестовом Instagram-аккаунте бот отвечает сам, а в режиме оператора предлагает варианты, и выбранный уходит клиенту.

### Этап 5. Каталог и поиск

1. `docker-compose`: Qdrant, Elasticsearch с плагинами `analysis-ukrainian` (во встроенных анализаторах ES украинского нет) и `analysis-icu` (общий анализатор для остальных языков).
2. `search/`:
   - общий интерфейс `search(kind, query, filters, limit)`;
   - ES — каталог (морфология uk/ru, опечатки, фильтры по характеристикам);
   - Qdrant — база знаний и смысловой поиск по каталогу; эмбеддинги OpenAI `text-embedding-3-large`, как в старом боте (своих моделей не держим);
   - фильтр по тенанту и языку.
3. Индексация — задачи в `jobs`: запись в ES и Qdrant одной задачей с повторами, пропуск неизменённого по хешу, `uuid5` для id.
4. Уточнение: до 100 кандидатов → один запрос к Jev. На каждого кандидата свой вопрос boolean «подходит под запрос клиента?» (ключ `cand:<id>`), все в одной пачке. Если нужен один лучший — один choice из кандидатов (до 255 вариантов). Какой способ точнее — сравнить на `make eval`.
5. База знаний: оценка найденных кусков, ни один не подошёл → «не знаю» или оператор.
6. Поле `choice` из каталога, выбор из последних показанных вариантов (`state.last_presented`, промпт `context_manager_select_service`).
7. Вопрос маршрута `search` включается.
8. Админка: источники, статус индексации, тестовый поиск.

**Тесты:** морфология («манікюр» находит «манікюру»), фильтры, «не знаю», выбор «давайте второй».

### Этап 7. Пороги Jev и сравнение с LLM

Сам Jev работает с этапа 1. Здесь — настройка по накопленному журналу `decisions`.

1. `policy.py` по каждому ключу вопроса: режим `jev | llm | shadow`, порог, что делать ниже порога (спросить LLM / переспросить клиента / оператор).
2. Теневой режим: Jev и LLM отвечают оба, используется основной, оба ответа пишутся в журнал.
3. Админка: по каждому вопросу — как часто Jev и LLM совпадают, как распределена уверенность, сколько ушло в запасной LLM; переключение режима и порога.
4. Подбор порогов по журналу и `make eval`.

Можно делать после этапа 3 (нужна админка), как только накопится журнал.

# Этап 5: каталог и поиск

Тесты проходят (прогон 2026-10-02), кроме 5 тестов морфологии ES: они идут только при
запущенном Elasticsearch. Elasticsearch и Qdrant поднимаются
вместе со всем остальным: `make up` (`docker-compose.yml`).

## Что сделано

- **Два индекса:**
  - Elasticsearch (поиск по словам) хранит каталог. Индекс `{SEARCH_INDEX_PREFIX}catalog`.
    Свои анализаторы (правила разбора слов: «манікюру» → «манікюр») для uk / ru / en,
    для остальных языков — общий ICU. Плагины `analysis-ukrainian` и `analysis-icu`
    ставятся в образ (`docker/elasticsearch/Dockerfile`). Есть исправление опечаток.
  - Qdrant (поиск по смыслу) хранит каталог и базу знаний. Эмбеддинги (числовой «отпечаток»
    смысла текста) делает модель на роли `embed`. Коллекция своя на каждую модель:
    `{префикс}catalog__openai_text_embedding_3_large`.
- **Индексация — задачи в очереди `jobs`:**
  - товар или источник изменился → задача; одна задача на строку (повторные правки её
    не размножают);
  - неизменённое (тот же хеш содержимого) не индексируется второй раз;
  - выключенный товар уходит из индексов, но остаётся в базе;
  - индекс недоступен → повтор с паузой, строка остаётся «ожидает»;
  - база знаний режется на куски по ~1200 знаков с нахлёстом 150, каждый кусок начинается
    с названия источника;
  - без модели `embed` каталог работает только по словам; базе знаний модель обязательна
    (ошибка `search.embed_unassigned`).
- **Поиск в ходе диалога** (шаг 4):
  - вопрос маршрута `search`: none / knowledge / catalog / both. Задаётся, только если у
    тенанта есть проиндексированный каталог или база знаний;
  - ищем по переписанному тексту в обоих индексах, списки сливаются (RRF — честное
    смешивание мест из двух списков);
  - **уточнение:** до 100 кандидатов → одна пачка вопросов Jev «подходит под запрос
    клиента?» (`cand:<n>`, `kb:<n>`), порог 0.5. В ответ идут до 5 товаров и 4 кусков
    базы знаний;
  - ничего не подошло → бот говорит, что не знает (старые правила `i_dont_know_rules`).
    Настройка тенанта `unknown_answer: handover` — ещё и передать диалог человеку;
  - индекс упал → ход не падает, в трассе пометка `words_error` / `vectors_error`.
- **«Давайте другий»:** показанные клиенту товары сохраняются в
  `conversations.state.last_presented`. Переписывание видит их списком и раскрывает
  «другий» / «той за 500» в название.
- **Поле сценария типа `catalog`:**
  - в настройке поля — категории и сколько вариантов предложить (2–10, `max_options`);
  - **что бот показывает вместе с вопросом** (`scenarios/catalog.py`, в трассе хода —
    `catalog_ask`):
    - позиций в категориях поля не больше `max_options` → все, нумерованным списком с
      ценами (`source: all`);
    - позиций больше → только те, что подходят под слова клиента: найденные шагом поиска
      (`search`), а если маршрут поиск не запускал — 30 ближайших позиций проверяет Jev
      (вопросы `opt:<n>`, тот же порог 0.5; `named`). «Хочу на манікюр» → два маникюра с
      ценами. Подходит больше, чем `max_options`, → первые и пометка «есть и другие».
      Ответ Jev на `opt:<n>` берётся как есть, даже когда он не уверен: общее правило
      `opt:*` «оставить ответ Jev» (админка → «Решения»). Без правила неуверенные ответы
      переспрашивались у LLM — это лишний вызов модели (около 3 с), а ответ не менялся;
    - ничего не подошло (клиент услугу не называл) → вместо позиций бот называет
      категории каталога (`categories`; от 2 до 12, порядок — как в списке категорий
      поля, иначе по алфавиту). Клиент выбрал категорию → её позиции списком;
    - показанные позиции становятся `last_presented`, поэтому «давайте другий» работает;
  - модель ответа называет услуги, товары и цены только из этого списка, категорий и
    найденного: правило `ask_next.from_catalog` в промпте `scenario_step` (иначе она
    придумывала примеры по описанию бизнеса);
  - модель извлечения выбирает только из списка (показанные + найденные сейчас + поиск
    по полю, до 20); выбор не из списка отклоняется (`unknown_item`);
  - в поле пишется название товара, в результате — его `external_id` (`refs`).
- **Админ API** (`/v1/admin/tenants/{id}/…`):
  - `catalog` — список с поиском и категориями, создание, правка, удаление;
  - `catalog/import` — CSV (`,` или `;`, колонки `attr:<имя>` для характеристик, `|`
    между значениями) или JSON. Всё или ничего: одна плохая строка — ничего не
    сохраняется, ошибка с номером строки. `deactivate_missing` выключает товары,
    которых нет в файле;
  - `knowledge` — источники базы знаний;
  - `search/status` (сколько проиндексировано, `?ping=true` — проверить индексы),
    `search/reindex`, `search/test` (тестовый поиск: кандидаты и что подошло).
  - Оператор только смотрит и пробует поиск; менять может админ.
- **Админка:** разделы «Каталог» и «База знаний», статус индексации, тестовый поиск,
  в редакторе сценария — тип поля «из каталога», в настройках — `unknown_answer`.

## Как попробовать

```bash
make up                            # всё, вместе с ES и Qdrant; миграции применяются сами
make zama c="models add openai/text-embedding-3-large --from-gateway --kind embedding"
make zama c="models assign embed openai/text-embedding-3-large"
# админка → Каталог → Импорт CSV; Поиск → «Проверить»
```

## Проверено вживую (2026-10-05)

На настоящих Elasticsearch 8.17.4 (оба плагина) и Qdrant v1.13.6, тенант `demo`,
14 услуг в каталоге и один текст в базе знаний:

- индексация: 14 документов в ES, по коллекции в Qdrant на каталог и на базу знаний;
- каталог: формы слов («манікюру»), опечатка («маникур»), русский запрос к украинскому
  каталогу («постричь ребёнка» → «Дитяча стрижка»), запрос только по смыслу («хочу
  розслабитись після роботи» → «Масаж спини»), посторонний запрос → ничего;
- база знаний: вопросы на украинском, русском и английском находят нужный кусок;
  вопрос без ответа → ничего;
- в ходе: цена из каталога, ответ по базе знаний, «не знаю», выбор услуги в сценарии
  записи («давайте другий»).

Что нашлось и исправлено:

- **Диск заполнен больше чем на 95% → ES не создаёт индексы** (запрос висит 30 секунд,
  существующие индексы только для чтения). В dev-`docker-compose.yml` проверка места
  выключена. На сервере так делать нельзя — там нужно свободное место.
- **Jev видел только первые 600 символов куска базы знаний**, а кусок — до 1200. Ответ
  из второй половины куска отбрасывался как «не подходит». Теперь кусок показывается
  целиком.

- **Бот не показывал услуги из каталога, когда клиент называл услугу, а Jev отвечал
  «поиск не нужен»** («Хочу на маникюр» → «Який саме вид манікюру?» без вариантов), а на
  первый вопрос придумывал список по описанию бизнеса («манікюр, педикюр чи стрижка»).
  Теперь список не зависит от ответа Jev про поиск, а без названной услуги бот называет
  категории каталога. Проверено в песочнице: «хочу записаться» → «Волосся, Нігті,
  Обличчя, Тіло»; «Хочу на маникюр» → два маникюра с ценами; «давайте другий» → выбран
  второй; «нігті» → 4 услуги для ногтей; «хочу на тату» → категории.

Что стоит улучшить: кусок базы знаний склеивается из соседних абзацев до 1200 символов,
поэтому в один кусок попадают разные темы (дети, оплата, парковка). Jev точнее отвечает
на куски об одном; заголовок (`# …`) мог бы начинать новый кусок.

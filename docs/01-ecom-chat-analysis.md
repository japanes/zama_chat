# Разбор старого чат-бота (ecom-chat)

Исходник: `/home/japanes/projects/ecom-chat`. Пути ниже указаны относительно него.
Дата разбора: 2026-09-30.

## Коротко

- Весь бот держится на одном WebSocket-эндпоинте FastAPI (`app/routes/chat.py:614`). Логика собрана в класс `Chatbot` на 2458 строк (`app/llm/chat.py`).
- Настройки и история лежат в Directus, бот читает их по REST без кэша. Своей БД у бота нет.
- Одно сообщение пользователя — это до 5 **последовательных синхронных** вызовов LLM.
- Стриминг ненастоящий: ответ целиком генерируется и уходит одним куском. **Переход на POST ничего не теряет.**
- Поиск устроен так: Qdrant ищет по базе знаний, Elasticsearch используется только для подбора услуг.
- Режима оператора (когда человек подключается к чату) нет.

## Как проходит одно сообщение

```
Сайт → replaichat.js → iframe chat.php → replai.js → WS /chat/ws (app/routes/chat.py:614)

open:    проверка Origin → Chatbot.init (llm/chat.py:172)
         [грузит из Directus клиента, промпты, сценарии, агентов; создаёт ES, Qdrant, pymorphy]
         → создаёт клиента в CRM (schedule_customers, customer_sessions)

message: chatContext (llm/chat.py:872)
           ├─ определение языка (lingua, детектор создаётся заново каждый раз)
           ├─ загрузка ВСЕЙ истории (одна строка Directus `messages`)
           ├─ LLM#1(+1b) "context manager" → {question, type, role, lang, tags}
           ├─ сценарии: LLM#2 ScriptCheck (извлечение полей для записи)
           └─ сохранение (PATCH всей строки)
         chatRetriever (llm/chat.py:1947)
           ├─ Qdrant top-4 по переписанному вопросу, без фильтров
           └─ сборка промптов (core/prompts.py:321, :401), плейсхолдер %SERVICES% → ES+Qdrant
         Chatbot.stream (llm/chat.py:2252)
           ├─ LLM#3 основной ответ (НЕ стриминг)
           └─ LLM#4 quality manager (может переписать ответ)
         → start → stream{весь ответ} → end
         → колбэки сценариев (запись, email, Telegram) → сохранение (PATCH)
```

Telegram, Instagram и `GET /chat/` идут через тот же конвейер (`app/routes/chat.py:90-161`, `:176`, `:404`).

## Принципы, которые стоит сохранить

Это не код, а идеи, на которых строим новый бот.

1. **Ход диалога как конвейер:** понять → (сценарий) → найти → ответить → проверить → выполнить действия.
2. **Context manager:** переписывает сообщение пользователя в самостоятельный вопрос и определяет намерение (intent). Пример: «а сколько стоит?» превращается в «сколько стоит маникюр в салоне на Шевченко?».
3. **Модель под каждую роль:** для context manager, основного ответа и проверки модель выбирается отдельно и настраивается на каждого клиента (тенанта, т.е. салон/компанию).
4. **Промпты по типам и редактируемый список намерений** (`context_manager_types`).
5. **Сценарии (scripts):** пошаговый сбор данных (запись, отмена, перенос), в конце выполняется действие, например создаётся запись.
6. **Персоны (agents):** роль, цель и ограничения бота, включаются по триггеру.
7. **Подробный лог каждого хода:** промпты, найденные документы, токены, цена. Очень полезно для отладки в админке.
8. **Реестр знаний:** какой источник (Q&A, страница, файл) лежит под каким id в векторной БД.
9. **Факты об услугах** (цена, длительность, категория) используются как структурные фильтры, а не только как текст.
10. **Фоновая индексация:** запускается сразу при изменении данных, плюс ночная страховочная переиндексация.

## Проблемы: почему код не переносим

### Архитектура и производительность
- Огромные файлы: `llm/chat.py` (2458 строк), `llm/services.py` (2939), `core/prompts.py` (1235). Всё состояние лежит в одном глобальном словаре (ContextVar, `core/session_context.py`).
- Модули `routes/*` одновременно служат слоем доступа к данным, поэтому Directus протянут через весь код.
- Синхронные `requests` и вызовы LLM SDK внутри async-кода: один медленный запрос тормозит весь воркер.
- На каждое подключение всё создаётся заново: pymorphy, клиент ES, проверка индекса, подключение к Qdrant, полная загрузка конфигурации. Клиент LLM SDK создаётся на каждый вызов.
- Около 680 строк мёртвого кода в `llm/chat.py:1050-1730` (за условием `len(messages) > 100000`) и около 670 в `llm/services.py` после `return result; exit()`.

### Контекст и история
- Нет бюджета токенов и нет сжатия истории: вся история уходит в каждую модель, поэтому каждый следующий ход дороже предыдущего.
- История одного диалога хранится как одна JSON-строка и перезаписывается целиком несколько раз за ход.
- «Не знаю» определяется по эмодзи `:-(` / `:-/`, которое модель просят добавить в ответ.

### Поиск (Qdrant + Elasticsearch)
- **Знания:** Qdrant top-4 без фильтров (даже по языку), порог 0. Одна и та же услуга на 3 языках может занять 3 из 4 мест.
- **Подбор услуг** (`%SERVICES%`, `llm/services.py:645`): Qdrant k=50, затем на **каждый** результат 3 запроса в ES. Это до 150 запросов на один вопрос, а в запасном пути до 3000.
- Итоговая оценка — ручная формула `0.55·cos + 0.1·jaccard + 0.35·bm25`. BM25 не ограничен сверху, поэтому он перевешивает остальное.
- Слова лемматизируются (приводятся к начальной форме) только в запросе, а в индексе ES стемминга нет. Итог: «манікюр» не находит «манікюру».
- `_ukrainian_` не является встроенным списком стоп-слов ES, поэтому украинские стоп-слова не удаляются.
- Вероятно, теряется большая часть кусков (чанков) страниц и файлов: на источник выдаётся один id, а кусков много (`llm/learning.py:199-211`). **Это надо проверить на реальных данных.**
- Любое изменение услуги вызывает полную переиндексацию с платными эмбеддингами OpenAI, причём синхронно, внутри HTTP-запроса CRM.
- ES и Qdrant не согласованы между собой: ошибки проглатываются, и при таймауте данные есть в одном хранилище и отсутствуют в другом.
- Реранкер (bge-reranker, модель повторной сортировки результатов) написан, но выключен.
- Эмбеддинги бота: OpenAI `text-embedding-3-large` (3072 измерения). Поиск маркетплейса (`llm/public_search.py`) — отдельный стек на self-hosted e5-large, **бот его не использует**.

**Вывод по ES:** боту ES нужен только для подбора услуг по словам, и сделано это неэффективно. Маркетплейсу ES оправдан (гео, автодополнение), но это отдельная задача.

### Безопасность и баги
- Нет авторизации. Тенант берётся из атрибута виджета, проверяется только заголовок Origin, а его легко подделать вне браузера. Без авторизации открыты `GET /messages/...`, `/prompts/{client}`, `/clients/{id}`, `GET /chat/`.
- Режим `logs=1` отдаёт любому клиенту внутренние промпты и найденные документы.
- Возможна утечка данных между тенантами: изменяемые атрибуты класса `Chatbot` (`llm/chat.py:80-170`) общие для всех подключений воркера.
- В Telegram и Instagram все пользователи одного тенанта попадают в одну сессию (`routes/chat.py:266-278`, `:445-458`).
- События (например, «запись создана в чате») обрабатываются только на 1 из 4 воркеров (`main.py:72-83`), остальные теряются.
- Ошибка в подсчёте стоимости (`routes/chat.py:797-799`).
- Токены Instagram и Telegram лежат в комментариях `routes/chat.py:180-183` и `:572`, а файл есть в git.

## Что сейчас делается через Directus

1. Настройки чата: приветствие, имя бота, быстрые вопросы, цвета, логотип, профиль поведения.
2. Код для вставки на сайт (ключ + разрешённый сайт).
3. База знаний: Q&A, сайты (одна страница или обход целиком), файлы.
4. Справочник услуг и категорий.
5. История диалогов и список «бот не знал ответа».
6. Расходы на LLM.
7. Переиндексация.
8. Создание компании (копируются промпты по умолчанию), пользователи, уведомления.
9. Напрямую как таблицы Directus, без отдельного интерфейса: модели, промпты, сценарии, агенты, типы намерений, пороги поиска.

## Связи с ecom (в новом боте станут API)

- **Чтение:** услуги и категории, мастера, локации, расписание и свободные слоты, записи клиента (`routes/schedule.py`).
- **Запись:** создать, отменить или перенести запись; найти или создать клиента (`scripts/script_callback.py`).
- **Обратная связь:** при изменении каталога в CRM ecom сейчас сам переиндексирует бота (`routes/schedule.py:2339…` → `services/tenant_indexer.py`). В новом варианте ecom будет вызывать webhook бота.
